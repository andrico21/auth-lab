R2 · P2Keep realm validation and Apply atomic

New regression. The form accepts realm strings up to 2,048 characters, but the AD constructor now accepts at most 254. Apply commits the value before constructing the new model. A 255-character value throws after commit, with the validation error region hidden. Subsequent corrected Apply also throws because it consults the invalid current model. Reset environment recovers.

Locations: src/kerberos-ad-lab.js:143, src/runtime-environment.js:62 and :64, src/app.js:468 (Apply handler).

  1. Choose lab-ad-first-sign-in and expand Use your environment.
  2. Enter 255 copies of R in Kerberos realm, then Apply.
  3. The handler throws Use a valid example Kerberos realm.; the applied realm is already 255 characters and the inline error remains empty/hidden.
  4. Replace the draft with CORP.EXAMPLE and Apply again. It throws again and retains the invalid applied value. Reset works.

The same comparison against HTML2 did not throw and allowed the corrected Apply. This is a validation/transaction problem; the review does not prescribe a universal RFC realm-length limit.

Required correction: use a shared input contract for the form and constructor. Validate and construct the candidate before committing it, and surface a recoverable inline error if construction fails. Keep the previous applied context and playback state intact on rejection. Entering a valid correction must work without requiring Reset.

Acceptance: test the chosen limit and the adjacent rejected length through the actual Apply handler; test the current 255-character reproduction and a 2,048-character value; verify visible error/field association, unchanged committed context, successful corrected Apply, and Reset. Keep the original R1 tests passing.

R3 · P2Interpret or reject realm-qualified service principals

Existing input-contract defect, newly identified. The UI explicitly accepts and recommends a service principal such as HTTP/server.corp.example@CORP.EXAMPLE. The model consumes the entire string as the service name while independently taking the service realm from the account-realm field.

Locations: src/runtime-environment.js:65, src/kerberos-ad-lab.js:142 (context), :171 (definitions), :244 (reply construction).

Reproduction: in lab-ad-first-sign-in, enter cifs/review.other.example@OTHER.EXAMPLE as the service principal, leave Kerberos realm blank, Apply, and inspect the service TGS reply and final state:

Ticket.sname = cifs/review.other.example@OTHER.EXAMPLE
Ticket.realm = A.EXAMPLE
EncTGSRepPart: for ...@OTHER.EXAMPLE; srealm=A.EXAMPLE
proofs.tgsService.realm = A.EXAMPLE
sessions.serviceAuthenticated = true
sessions.resourceAccess = true

In the accepted principal notation, the unescaped @ suffix specifies the realm. RFC 4120 separates the principal name from its realm in ticket and protected reply fields. Treating that suffix as ordinary service-name text changes the meaning of the entered principal. See RFC 1964 §2.1.1 and RFC 4120 §5.2.2, §5.3, §5.4.2.

HTML2 already had the qualified-name/wrong-realm combination. This finding does not reopen the original R1, whose unqualified service-name mismatch is now fixed.

Required correction: define one parsed service identity and derive displayed name, service realm, protected reply, proof and cache from it. For these fixed single-realm presets, the bounded solution is to accept/normalize a matching realm qualifier and reject a conflicting qualifier with a clear message pointing to the separate cross-realm lessons. Do not silently move the account realm or imply that arbitrary forest referrals have been generated. If only unqualified SPNs are supported, validate and describe that restriction explicitly.

Acceptance: cover an unqualified SPN, a matching qualifier, and a conflicting qualifier in both baseline AD and Keycloak bridge Apply flows. Rejection must preserve the previous model; accepted values must agree across request, ticket name/realm, protected reply, cache and focused Send. Include Reset/base-fixture preservation.
