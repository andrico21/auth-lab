<h2 id="required-correction-wp-r06-b">Required correction: WP-R06-B</h2>
<h3 id="p2-internal-password-passes-appear-as-completed-public-apis">P2
— Internal password passes appear as completed public APIs</h3>
<p>The new source lifetime is correct, but its result classification
still teaches the wrong boundary. In
<code>src/pam-existing-integration.js</code>, line 123 writes
preliminary and update statuses into
<code>workstation.pamResults</code>. In <code>src/app.js</code>, lines
666–679, <code>renderPamConfiguration()</code> reads the complete result
map and renders it under <strong>“Completed API aggregate
results.”</strong> It does not distinguish the internal entries from
public <code>password</code>, <code>authenticate</code> or
<code>account</code> results.</p>
<p>This is a visible contradiction at an intermediate prefix: the
evaluation panel correctly says <strong>“Pending: current API call has
not completed”</strong>, while the completed-API disclosure already
contains <code>prelim: PAM_SUCCESS</code>. Later, <code>update</code> is
also shown in the completed-API collection. The internal results are
useful evidence; their current classification is wrong. The issue is
observable in the source application and actual supplied standalone
script, not merely in an abstract JSON inspection.</p>
<p>Open <strong>LLOG04 / default</strong>, select source index
<strong>14</strong> (zero-based),
<code>lab-llog04:password-preliminary</code>, and expand the
completed-results disclosure. Both loading modes show:</p>
<pre class="text" tabindex="0" role="region" aria-label="Reproduction source 1"><code>API aggregate return: Pending: current API call has not completed

Completed API aggregate results
{
  "authenticate": "PAM_SUCCESS",
  "account": "PAM_NEW_AUTHTOK_REQD",
  "prelim": "PAM_SUCCESS"
}</code></pre>
<p>The default sequence is public call at index <strong>13</strong>,
internal preliminary result at <strong>14</strong>, internal update
result at <strong>23</strong>, and the actual public return at
<strong>25</strong>. The update entry is likewise placed in the
public-completion collection. Across the six registered reached-change
variants, the UI probe reproduced <strong>56 intermediate positions per
mode</strong> with this misclassification. These are repetitions of one
defect.</p>
<p>The shared display also affects <strong>PAM01 /
password-change-required / change-success</strong>, source index
<strong>21</strong>, <code>lab-pam01:api-2</code>. The same disclosure
contains <code>prelim: PAM_SUCCESS</code>, while <code>password</code>,
<code>setcred</code>, <code>open</code>, <code>close</code>,
<code>setcred-delete</code> and <code>end</code> have the value
<code>not evaluated</code>. Those entries are not completed public
results either. This is the same classification problem in a shared
consumer; the previously closed WP-R05 internal/caller-flag finding
remains closed.</p>
<h3 id="why-the-passing-tests-miss-it">Why the passing tests miss
it</h3>
<p>The new regression file correctly asserts that the public
<code>pamResults.password</code> is absent before completion, that only
one public result artifact exists, and that the current evaluation’s
pending row is present. Its six rendered-panel tests select the
<code>API aggregate return</code> row. None of those conditions prevents
an internal <code>prelim</code> or <code>update</code> entry from
simultaneously appearing in the separate “Completed API aggregate
results” disclosure. Both sets of observations can therefore be true in
the same passing run.</p>
<p>The worker’s intentional result-map change is disclosed, and
excluding explanatory <code>pamEvaluation</code>/<code>pamResults</code>
from operational final-core comparison is reasonable. That exclusion
does not validate how the changed result map is presented. Keep the
operational comparison and add a direct classification contract for the
disclosure.</p>
<h3 id="implementation-requirements">Implementation requirements</h3>
<ol type="1">
<li><strong>Represent public API results and internal dispatch results
as distinct categories.</strong> Use an explicit projection for internal
pass results, with an independently labelled disclosure such as
“Internal password dispatch results.” An equivalent typed result
structure and explicit renderer partition is acceptable. Existing
canonical maps may remain compatible if the renderer accurately
classifies their entries; no state-schema migration is required merely
to fix this presentation. Do not rely on scenario-name-specific
presentation patches.</li>
<li><strong>Keep completed public API results truthful.</strong> Its
password-change entry appears only when the one public call completes.
Preliminary/update entries must never appear in that public category,
including after final completion or on failure. Previously completed
authentication/account results remain legitimate historical public
results and should stay visible. <code>not evaluated</code> placeholders
belong to a pending/not-started category, never the completed-results
category.</li>
<li><strong>Keep internal evidence visible and correctly timed.</strong>
Show preliminary/update status only after the respective dispatch
completes. Explain that these statuses belong to internal passes of the
enclosing <code>pam_chauthtok</code>, not separate application calls.
Preserve internal combined flags, physical module rows and returned
status. Do not delete this evidence merely to make the public disclosure
pass.</li>
<li><strong>Preserve the verified lifetime.</strong> One
caller-only-flags public call, pending status across
conversation/backend/preparation steps, one final public result, no
application-held internal phase-return artifact. Preliminary failure
must stop before candidate collection and update. Keep the existing
success, policy rejection, backend failure, unsupported-consumer and
post-change-account behavior.</li>
<li><strong>Preserve custody and replay.</strong> Do not recreate the
old password, extend its lifetime, repeat its verifier operation, clear
previously completed public results, change business outcomes or make
rendering depend on navigation history. Full, field-filtered and
exact-object views must agree at the same canonical prefix, including
after rewind.</li>
</ol>
<p>A generic rename of the mixed disclosure is insufficient unless the
display also clearly identifies which rows are internal and which are
public. The learning goal is for an operator to understand who calls the
API, who performs each internal pass, and when control returns to the
application.</p>
<h3 id="acceptance-checks-for-the-correction">Acceptance checks for the
correction</h3>
<p>Use the six existing LLOG04 variants: <code>default</code>,
<code>new-policy-denied</code>, <code>update-failed</code>,
<code>directory-unreachable</code>, <code>directory-online</code>, and
<code>post-change-account-denied</code>. Also retain the additive
<code>prelimOk:false</code> factory fixture; it is not a new registered
scenario or variant.</p>
