<h2 id="wp-r06-a-p2-sudo-aggregate-uses-a-password-already-released">WP-R06-A
— P2: sudo aggregate uses a password already released</h2>
<p><strong>Locations:</strong>
<code>src/pam-existing-integration.js:121</code>; the sudo input/check
is authored at <code>src/linux-elevation-lab.js:44</code>.</p>
<p>The candidate-04 follow-up changes aggregate dependencies from all
original objects to <code>options.checks[].object</code>. That fixes
LLOG01 because its checked object is a retained verifier. In sudo, the
checked object is the transient raw password. A checked input is not
automatically a reusable verification result.</p>

<p>The bounded 55-variant existing-consumer sweep finds it in eight sudo

<p><strong>Required correction:</strong> choose aggregate evidence by
its actual role. Consume an already-created module result or explicit
verification-result artifact; retain genuine non-secret evidence only
where needed. Preserve the accepted-state milestone and verifier
provenance. Do not prolong or recreate password custody to satisfy an
artificial aggregate dependency, and do not hide the offending history
row while leaving the source operation intact.</p>
<p><strong>Acceptance:</strong></p>
<ul>
<li>Every raw-password use in the six existing consumers / 55 variants
has owner custody at the actual consuming boundary. A use-and-release at
one physical module boundary is valid; a later use after that release is
not.</li>
<li>Each of the eight fresh-password sudo variants has exactly the real
module/backend password use. Its aggregate is absent from both password
histories.</li>
<li>Reused/exempt/no-prompt controls do not acquire a fabricated
password input. Wrong-password denial and later account denial keep
their original outcomes.</li>
<li>Full, field and exact-object views agree immediately before the
physical operation, after release, at aggregate completion, and after
rewind. Preserve the corrected LLOG01 behavior.</li>
</ul>

</div><p>The application creates and sends both argument artifacts. The
held-object projection delivers the preliminary return to the
application before the second call and ultimately gives it both
phase-return artifacts. The rendered panel marks each aggregate
completed. Therefore this is more than an imprecise step title.</p>
<p>The inventory identifies <strong>12 malformed public controls across
six variants</strong>: default, new-policy-denied, update-failed,
directory-unreachable, directory-online and post-change-account-denied.
Four reached-change variants were also exercised in the source and
actual emitted UI, together with the no-change consumer control.</p>
<p>The pinned Linux-PAM <code>pam_password.c</code> rejects
application-supplied internal phase bits. A valid public call receives
only the caller flags; libpam combines them with its own
preliminary/update flag during internal dispatch. Preliminary success
leads to update within that same call. The function then returns one
public result. The actual retained implementation was inspected, and the
official upstream indexed file corroborates this behavior.</p>
<p><strong>Required correction:</strong> represent one public
<code>pam_chauthtok(PAM_CHANGE_EXPIRED_AUTHTOK)</code> lifetime. Inside
it, show the preliminary dispatch, required conversation/backend work
and update dispatch, followed by one public aggregate. Keep full
combined flags on internal module records. They must not become
caller-created arguments or separately delivered public completions. Use
the corrected PAM01 lifecycle as a reference.</p>
<p>Preserve authority writes, secret collection before validation,
failure outcomes and post-change account checks. Do not change the
intended valid demonstration into a <code>PAM_SYSTEM_ERR</code> scenario
