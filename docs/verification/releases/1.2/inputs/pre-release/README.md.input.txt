## Architecture and scope

**Single Keycloak realm**, with OIDC selected, uses only the application's OIDC client registration in Realm A. A performs the configured password, TOTP or WebAuthn checks itself, establishes its local SSO session and issues the app's code and tokens. Its WebAuthn RP ID is `idp1.example.test` and origin is `https://idp1.example.test`; enrollment begins with a verified A account. There is no broker registration, B redirect, B code/token exchange or imported-identity mapping. Both the native loopback and network web callback variants retain PKCE. All seven provider-based learning journeys support this setup.

The application's **client_id** is assigned during registration and configured before login; it is a public identifier, not a per-login random value or a client secret. The authorization request carries it through the browser. A retains the client binding with the request/code. The unauthenticated public native client sends `client_id` in its token-request form body. In the illustrated confidential web variant, the backend uses the client ID as HTTP Basic's encoded username with its secret; this request does not duplicate `client_id` in the body. A constructs the ID token's `aud`, and the application checks that `aud` includes its registered ID. The ID token does not gain an invented `client_id` claim. Each illustrated `aud` occurrence has its own recipient value: the upstream ID token names Realm A’s broker client, while Realm A’s application ID token names the application’s registered client ID. Focused replay preserves the value that each receiver actually checks, including runtime client-ID projection, rather than showing a combined glossary example. SPA/BFF ID-token audiences and API access-token audiences remain separate. Direct application FIDO2 journeys have no OAuth client ID.

The native app is a **public OIDC client of Realm A**, using Authorization Code + PKCE S256. It first binds the loopback listener `http://127.0.0.1:54321/callback`; this is an illustrative port. A real native app typically selects an available ephemeral port and registers compatible loopback redirects. The system browser ultimately delivers A's authorization code to this listener. The app exchanges that code directly with A using its `code_verifier`; it has no `client_secret`.

With OIDC selected, the network web app is a **confidential server-side OIDC client of Realm A**. Its callback is `https://app.example.test/oidc/callback`. The backend generates and retains state, nonce and its PKCE verifier, redirects the browser, receives A's code over HTTPS and redeems it using PKCE plus HTTP Basic client authentication. It validates A's ID token, keeps the tokens on the backend and creates an opaque browser session cookie. The app's backend credential and A's broker credential are separate. Participant roles identify its server-side boundary; inventory layouts never reassign that ownership.

For an OIDC upstream hop, Realm A brokers identity to **Realm B** through a separate, confidential OIDC client. It has its own `state`, `nonce`, callback and authorization code. A redeems B's code over a server-to-server HTTPS connection and validates B's ID token before resolving A's own user. A then issues its own authorization code and tokens to the native client. On OIDC token responses, ID-token claims such as `iss`, `aud`, `sub` and `nonce` are nested inside the decoded `id_token`, not additional top-level token endpoint response fields. This core journey focuses on the successful brokered exchange. The universal lab separately animates trusted key retrieval/rotation, API introspection, consent, first-broker-login linking and selected error/session branches. Optional UserInfo and every provider-specific action are not expanded into every core configuration.

The **external OIDC provider** option represents a different identity-provider product, rather than another Keycloak realm. It has its own `iss`, authorization/token endpoints, keys, accounts, sessions and passkey RP scope at `login.partner.example.test`. Realm A uses its `external-idp` broker alias and validates that provider's OIDC result before issuing A's own tokens. The chosen factor must be supported and configured by the external provider; its browser form names and credential policies are provider-specific. This is a generic interoperability example, not a claim about one named vendor. The native app's PKCE is between the app and A, and is not forwarded as the broker's proof.

WebAuthn happens on **B's HTTPS origin** with B's configured **RP ID**. The browser constructs `clientDataJSON`; the authenticator signs `authenticatorData || SHA256(clientDataJSON)`. PINs, biometric samples and credential private keys remain local/protected. Realm B verifies the assertion using its stored credential public key. Realm signing keys sign OIDC tokens separately. The registration scenario begins with an already verified B account. A real realm path is not an RP ID: realms on the same hostname may share the RP ID/origin while maintaining different account and credential records.

**FIDO2** combines W3C WebAuthn and FIDO Client-to-Authenticator Protocols. A FIDO2-capable YubiKey uses **CTAP2** over a supported USB/NFC transport; Windows Hello uses the platform authenticator interface. The browser invokes `navigator.credentials.get()` or `.create()` and the local client manages the device protocol. For the illustrated security-key PIN path, the protected PIN/UV exchange yields an encrypted local `pinUvAuthToken`; the client derives `pinUvAuthParam` for `authenticatorGetAssertion` or `authenticatorMakeCredential`. During registration, WebAuthn `residentKey: "required"` becomes CTAP2 MakeCredential `options.rk: true`, allowing later username-free discoverable-credential sign-in. This creation option is absent from GetAssertion. The PIN is not sent in plaintext to the key, and the RP server receives neither the PIN, local token nor CTAP authorization tag. The signed authenticator data reports successful user verification.

**Direct FIDO2 sign-in** makes the **web application itself the WebAuthn relying party**, using RP ID `app.example.test` and origin `https://app.example.test`. It creates the challenge, receives the assertion, verifies the registered public key and creates its own browser session. Keycloak and the external IdP are inactive in this direct journey; there is no OAuth code, PKCE exchange or OIDC ID token. Direct registration starts with a verified application account and stores its public-key credential record. Selecting a direct journey fixes the application to the HTTPS web RP and disables the unused upstream selector. YubiKey is selected initially; Windows Hello remains an alternative. This differs from the brokered passkey scenario, where the upstream IdP verifies WebAuthn and the application receives an OIDC result from A.

TOTP setup provisions a **shared secret** from B into the authenticator app, represented as an `otpauth://` QR payload. This URI is a common convention, not an RFC-defined format. At sign-in the app computes a time-based code locally; the person enters it in B's browser form, and B independently checks it. The secret is not sent again with the code. The public, fixed RFC test seed and timestamp are deliberately used in this simulation; **none of the displayed values are production credentials**. Realm A and the native app receive the resulting identity, not the TOTP seed or code.

**Password + TOTP** represents a configured MFA browser flow. **Passkey + TOTP** represents an explicitly configured custom B flow with a required OTP step after passkey verification; enabling passkeys alone does not enable this sequence. Login journeys assume a fresh session. Existing SSO, fallback paths and assurance mappings can change the production flow. Requirements based on `acr` or `amr` need agreed policy and claim mapping/enforcement across the broker. This app illustrates the protocol; it does not configure a real Keycloak server or perform live authentication.

**Password only** requires the upstream account password without passkey or OTP. **One-time code only (TOTP)** first identifies the account by username and then validates its previously enrolled authenticator-app code. This is explicitly configured passwordless authentication using one possession factor; it is not MFA or the default Keycloak browser flow. Account identification alone never authenticates the user. Email/SMS authentication codes and recovery-code authentication are distinct methods; they are not choices in the core TOTP selector. The universal lab separately models protected account recovery using a one-use Keycloak action credential.

Attribute animations are derived from explicit protocol-operation metadata, not by searching text or treating every glossary reference as a transmitted field. Local secrets and stored values remain local. Nested ID-token/WebAuthn/QR members identify their enclosing object. Connection routing uses participant rectangles, clearance and rounded orthogonal paths; it checks native and network layouts and routes self-actions around their actor. Participant movement is optional: dragging or arrow-key movement validates proposed routes, including focused self-actions, before committing the position. Accepted movement pauses playback and recomputes routes; an overlapping or unroutable proposal leaves the previous layout intact.

## SAML and encrypted tokens

Application ↔ Realm A and Realm A ↔ upstream IdP each select OIDC or SAML independently. This includes OIDC applications with a SAML broker, SAML applications with an OIDC broker, and SAML on both legs. A single realm supports OIDC or SAML directly. Password, TOTP and WebAuthn authenticate the person at the selected IdP before it returns the protocol result; those credentials are not assertions or grants.

The **SAML Web SSO** application uses a network web service provider and its HTTPS Assertion Consumer Service (ACS). SP-initiated login creates an `AuthnRequest` and later checks `InResponseTo`; configured IdP-initiated application login accepts an unsolicited response without inventing a request or `InResponseTo`. The upstream broker leg remains SP initiated. Choose signed HTTP-Redirect requests (raw DEFLATE → Base64 → URL encoding and detached query signature) or HTTP-POST requests (Base64 XML and XML signature). Responses use HTTP-POST. The recipient verifies trusted signatures, issuer, `Audience`, `Recipient`, destination, validity, saved transaction state where applicable and replay policy before creating its session. XML signatures in POST do not cover the separate `RelayState` form field; that state must be protected and checked separately. Keycloak’s SAML Client ID is the registered SP entity ID, represented as request `Issuer` and assertion `Audience`, rather than an OAuth `client_id` query parameter.

Optional **XML Encryption** encrypts a signed SAML assertion under fresh symmetric encryption material and wraps the key for the SP’s trusted public encryption certificate. The receiving SP keeps its private decryption key locally, decrypts, checks the inner signature and validates the assertion. A separate outer response signature is verified against trusted metadata. XML `EncryptedAssertion` and `CipherValue` are not JWE Compact Serialization.

The **JWE** selector protects application ID tokens, broker ID tokens, or both actual OIDC token-response legs. It does not encrypt SAML or turn a public client into a confidential client. Each selected issuer signs its normal ID token, creates a fresh Content Encryption Key (CEK) and IV, encrypts the signed token with illustrative `A256GCM`, wraps the CEK using illustrative `RSA-OAEP-256`, and returns a five-part compact `id_token`. The recipient unwraps with its local private encryption key, authenticates/decrypts the content, verifies the inner JWS with the issuer’s separate signing key, and checks OIDC claims against the original request. The readable protected header states `alg`, `enc`, `kid` and `cty`; claims, plaintext CEKs and private keys are not animated as network fields. Other access/refresh tokens retain their usual independent protection. Generic external-provider JWE retains the encrypted broker-token definition: local final assembly and the next wire transfer show the same five-part compact value. Recovered inner JWS and the recipient’s decoded claims appear in their identified local decryption/validation stages. Broker decryption uses Realm A’s ENC-use realm key, separate from realm signing keys and the confidential broker client secret. The examples are protocol simulations and perform no live cryptography.

The separate **SAML** and **JWE** index topics expose each hop's canonical fields and exact local/transfer operations. Inactive fields offer a control to switch to an applicable protocol. Credential-enrollment and direct application FIDO2 journeys do not invent SSO assertions or encrypted ID-token responses.

## Additional OAuth learning flows

The **Service account · client_credentials** walkthrough starts with a confidential background service registered in Realm A. Client authentication and Service account roles are enabled. The service constructs HTTP Basic client authentication, sends a direct `grant_type=client_credentials` request, and receives an access token for its own service-account identity. Realm A calculates the token's roles as the intersection of service-account assignments and the role scope mappings permitted by the client and its applied client scopes. The illustrated API audience comes from an explicitly configured mapper. Client secrets travel intentionally inside the HTTPS Basic header; the realm's private signing key remains local. This normal response contains no ID token, refresh token or end-user SSO session. The core grant ends with the token ready for API work. Separate universal-lab API and mTLS/DPoP scenarios animate credential presentation, validation, authorization and resource responses.

The **Device Authorization Flow** walkthrough separates a requesting limited-input application from the person's independent verification browser. Choose the public native client or confidential device service; neither requires an inbound application callback. The realm returns a private `device_code`, a human `user_code`, a `verification_uri`, optional `verification_uri_complete`, code lifetime and polling interval. The client keeps `device_code` private and shows the verification instructions and human code. The person opens the realm on another device, authenticates using the selected configured factor method and deliberately approves the requesting device. The client polls the token endpoint with the device-code grant URN and `device_code`. The animation includes `authorization_pending` and a deliberately early-poll `slow_down` example, after which the local interval increases by five seconds for every later poll. Successful approval and redemption return tokens to the requesting client, never to the verification browser. This example requests `openid`, validates the resulting ID token, and does not invent a request nonce or PKCE exchange. Visual speed controls do not change the protocol's real polling requirements.

The **CIBA · Poll delivery** walkthrough uses `login_hint`, `binding_message`, `auth_req_id`, its lifetime and a polling interval. A confidential consumption backend asks Realm A to authenticate the identified person on a separate authentication device. In the diagram, the right-hand service represents a controlled **AuthenticationChannelProvider integration**, not another Keycloak realm or a broker IdP. Realm A delegates to this trusted authentication service, which verifies the intended account, obtains explicit approval and sends an authenticated result notification back to A. The five selectable password/passkey/TOTP combinations illustrate factor policies that such a service can implement; enabling Keycloak CIBA does not install these device ceremonies automatically. The client polls using its own authenticated pending handle, then validates the returned OIDC identity result. There is no application authorization redirect, code, PKCE or original nonce in this Poll example. The protected authentication-service callback credential is distinct from a CIBA client notification token and never reaches either browser. Required capabilities, trusted channel configuration and matching account/transaction checks remain explicit.

The **Token exchange · Standard V2** walkthrough starts with an already-held, valid Realm A access token; its original issuance is a prerequisite. A confidential `requester-client` authenticates directly to the same realm and submits the token-exchange grant, `subject_token`, `subject_token_type`, `requested_token_type`, requested `audience` and `scope`. The source token's audience includes the requester. Realm A checks the requesting client, the Standard token exchange capability, the source token and configured authorization policy before returning a new access token with `issued_token_type`, `token_type`, lifetime and granted scope. This example narrows access to `orders-api` and `orders.read` under an explicit `downscope-assertion-grant-enforcer` client policy. Downscoping is not an automatic property of every Standard V2 exchange: configured optional client scopes can otherwise affect the result. The original token keeps its own validity; exchange neither revokes it nor performs a new user authentication. Private signing keys remain local, and source/result claims remain nested in their respective tokens. The universal lab separately covers ID-token/refresh-token results, Preview client delegation and external trust/legacy variants with explicit support notes.

The new models use cached journey data and authoritative per-step attribute-operation ledgers. The index distinguishes each grant's request objects, response members, nested claims and local policy inputs. Optional ID-token JWE protection also works on the actual Device Authorization and CIBA token-response leg, preserving those grants' claim sets without adding an Authorization Code nonce. Service-account and illustrated token-exchange responses contain access tokens, so their controls do not fabricate an encrypted ID token.

## Version 14 content security policy

The standalone HTML places an enforced Content Security Policy immediately after its charset declaration, before any executable code or stylesheet. `default-src 'none'` denies resources by default. Only the exact embedded JavaScript and CSS are authorized by SHA-256 hashes; the build computes these from the final emitted text, including script closing-tag escaping and whitespace. It normalizes CRLF/CR to LF before emission and hashing. No `unsafe-inline`, `unsafe-eval`, wildcard or `blob:` permission is granted. Data URLs are authorized only for images, to embed the supplied favicon set, never for scripts or styles. Rebuild after changing embedded code, CSS or icons; editing generated code without updating its policy makes its hash stop matching.

HTML event-handler attributes and inline style markup are forbidden. Actor coordinates, animated packets, progress and help positioning use individual CSSOM property assignments, which remain permitted by CSP. Static actor colors are in the stylesheet. `connect-src 'none'` blocks script-initiated connections; font/media/frame/object/worker/manifest loading, form submission and base-URL changes are also denied. Actor SVG art uses inline shapes and same-document fragment references, not external resources. Explicit documentation links still open when clicked: CSP resource restrictions do not disable ordinary hyperlink navigation.

The source `index.html` permits same-origin modules, its stylesheet and the supplied files in `assets/`, with the same restrictions on connections and HTML handlers. The build requires exactly one current source policy inside `head` before resources and one of each stylesheet/module/favicon placeholder. It replaces script/style permissions with exact hashes and embeds all three unchanged icon files as image data URLs. The resulting HTML, including its favicon and Apple touch icon, needs no sibling assets over HTTP or `file://`; Pages still stages only that one HTML file. `bun start` binds the development server to `127.0.0.1`.

This is defense in depth alongside existing text escaping, not a replacement for it or a guarantee against browser vulnerabilities. Meta CSP works with the offline file, but cannot enforce `frame-ancestors`, `sandbox` or reporting directives. To deny embedding when hosting the page, add the HTTP response header `Content-Security-Policy: frame-ancestors 'none'`; that header combines with, rather than replaces, the embedded policy. Trusted Types enforcement is not enabled: the app's existing escaped HTML templates remain in use.

Six dedicated checks verify the source policy, exact standalone hashes, altered-content mismatch, Windows newline normalization, script closing-tag escaping, fail-closed template validation and inert hostile identifier text. They are structural/build/DOM checks; the DOM harness does not enforce browser CSP. Native browser executables were unavailable at the historical version-14 delivery. Current review-candidate native results and loading-mode/CSP evidence are recorded separately under `docs/verification/held-objects/`; historical offline results do not establish native enforcement.

Primary references: [MDN CSP guide](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP), [CSSOM and style-src-attr](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/style-src-attr), [CSP3 meta delivery](https://www.w3.org/TR/CSP3/#meta-element), [SVG2 same-document references](https://www.w3.org/TR/SVG2/linking.html#processingURL).

`--source-version` deliberately ignores release/environment overrides for the committed-dist freshness check. CI first checks that source-version artifact, pinned cryptographic verification and the full test suite; a tag push or published release then compiles its own tag into the `auth-flow-studio-tagged` Actions artifact. Pages keeps the existing CI-gated `main` publication policy. Creating a release or publishing this change still requires explicit authorization.

CI checks the four generated public DNSSEC projections, executes the actual standalone boot/catalog smoke and runs `check-dnssec-numeric.mjs --out NEW_DIRECTORY` against four sealed independent numeric catalogs. This binds public RRsets, DNSKEYs, RRSIG bytes and displayed fingerprints to those inputs; the runner does not perform live DNS or browser cryptography. CI also checks the committed current-reference seal and performs a fresh offline Python/OpenSSL generation and verification replay.

The active verification-only [DNSSEC crypto profile](tools/verification/dnssec-crypto-current/profile.json) pins **cryptography 50.0.0**, dnspython 2.8.0, cffi 2.1.1 and pycparser 3.12. Its [upgrade record and exact proof identities](docs/dnssec-expansion/numeric/runtime-50.0.0/UPGRADE.json) bind the new wheel, source archive, raw upstream metadata, fresh installation receipts, runtime/licence provenance and separately sealed reference output. All 18 producers and 18 verifier/library programs execute under the new runtime; the 19 regenerated datasets retain the accepted public cryptographic bytes.

This offline profile requires **Linux x86_64, CPython 3.14.4, uv 0.12.10 and the system OpenSSL CLI**. These runtime prerequisites are not bundled. Acquiring Python may use the network; dependency installation uses only bundled wheels with a fresh external environment/cache, `--offline`, `--no-index` and `--require-hashes`. This is not OS-enforced network isolation or a Rust/source rebuild.

```sh
uv python install 3.14.4
bun run verify:dnssec --check
bun run verify:dnssec --out "$HOME/.cache/auth-lab-dnssec-current-50.0.0"
uv run --offline --no-project --python 3.14.4 python tools/verification/dnssec-crypto-current/replay.py --check docs/dnssec-expansion/numeric/runtime-50.0.0/reference
```

The `--out` directory must not already exist and must be outside the repository. Failed runs retain their actual command receipts; use a new directory after correcting a failure. The original `tools/verification/dnssec-crypto/` requirements, instructions, datasets and seals remain immutable **historical 46.0.3 evidence**, not the active install path. Do not install 50.0.0 into that historical profile or rewrite its hashes. Dependabot version updates now target the current sibling profile; alerts on the retained legacy manifest still require explicit owner disposition and are not dismissed by this migration. Application behavior is unchanged; release 1.1.1 changes only the compiled version label.

`bun run test` pins `--isolate --timeout=900000`: Bun otherwise shares one process and module registry across test files (unlike `node --test`), and its 5 s per-test default would abort the slowest DOM-harness checks, which take 165 s under Node and up to about 8 min under Bun.

The historical Node commands were:

```sh
node build.mjs
node --test tests/*.test.mjs
node tools/verification/independent-geometry-check.mjs
node tools/verification/compiled-bundle-smoke.mjs
```

Native-browser acceptance has a separate portable runner and prerequisites in [tools/verification/README.md](tools/verification/README.md).
