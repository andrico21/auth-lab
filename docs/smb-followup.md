## Authentication and access boundaries

- **Kerberos:** explicit domain credentials plus configured realm/KDC reachability, time and `cifs/files.corp.example` SPN enable AS/TGS acquisition without a client machine-domain channel. The KDC owns its own provisioned account key. The CIFS service ticket, ticket key, initiator subkey and Windows KILE AES **AP-REP acceptor subkey** are distinct. The acceptor subkey becomes the exported mechanism key. C acquires it only after validating AP-REP, then derives its SMB keys and verifies the final response.
- **NTLMv2 compatibility:** C sends challenge-bound proof, not the raw password/hash. S validates through its own FILES$ Netlogon secure channel. C need not contact D directly for this validation. The validator's SessionBaseKey, wrapped ExportedSessionKey, NTLM transcript MIC and SMB signing key have separate custody and uses. Protected Netlogon inner fields remain opaque until local DC processing.
- **SMB framing:** NEGOTIATE precedes SESSION_SETUP. Request/response MessageIds match. `STATUS_MORE_PROCESSING_REQUIRED` and an allocated SessionId are continuation state, not successful authentication. Final SPNEGO/AP-REP completion and signed SESSION_SETUP success share one carrier response.
- **Authorization:** signed TREE_CONNECT evaluates share connection policy; successful response returns TreeId and the share encryption requirement. CREATE checks requested rights against the share grant and then the file ACL. It opens an existing file using `FILE_OPEN`, returning a FileId only on success. READ and accepted file data are separate later operations.

The Microsoft [nonjoined-client SMB example](https://learn.microsoft.com/en-us/azure/storage/files/storage-how-to-use-files-windows#mount-the-file-share-from-a-non-domain-joined-vm-or-a-vm-joined-to-a-different-ad-domain) establishes that explicit domain credentials can support Kerberos without machine-domain membership. It does not justify claiming identical automatic credential selection on every on-premises client build. This lesson explicitly configures its Kerberos prerequisites and does not infer NTLM from join state.

## Signing, encryption and negative cases

Both peers chain `SHA512(previousHash || exact SMB message bytes)` from 64 zero bytes. The KDF context includes NEGOTIATE and SESSION_SETUP messages through the final client request: five messages for the NTLM exchange, three for the single-request Kerberos exchange. It excludes the final successful SESSION_SETUP response, which must be signed using keys already derived. See [server processing order](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/5ed93f06-a1d2-4837-8954-fa8b833c2654).

The [SP800-108 counter KDF](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/da4e579e-02ce-4e27-bbce-3fc816a3ff92) uses HMAC-SHA256, `r=32`, `L=128` and the 64-byte transcript context. Distinct NUL-terminated labels derive SigningKey, ApplicationKey, C2SCipherKey and S2CCipherKey. Keys are derived locally at both endpoints and never carried in SMB packet fields. The DC obtains none of these SMB traffic keys.

This profile sets `Session.EncryptData=false` and makes the reports share require encryption. Final SESSION_SETUP and both TREE_CONNECT messages are signed plaintext; TREE_CONNECT is excluded from share-only encryption. The verified response advertises `SMB2_SHAREFLAG_ENCRYPT_DATA`. CREATE/READ requests and responses, including file-access denial, use [AES-GCM encryption transforms](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/c4a91ca0-8d2e-404c-b9ac-3783ba9a01ef). Each direction has a separate cipher key and unique 12-byte nonce; the transform's AAD excludes ProtocolId and Signature. Its encrypted plaintext contains the entire inner SMB2 header/body. AEAD integrity replaces an extra inner SMB signature.

The models separate ciphertext receipt, authenticated unwrap and application acceptance. The invalid-final-signature case changes the actual wire signature, discards the response, and explicitly chooses the permitted disconnect. The invalid-GCM-tag case changes the actual wire tag, obtains no plaintext file data and **must disconnect**. In this single-channel, nondurable profile, client teardown frees active keys/session/tree/file handles; earlier successes remain historical replay events. It does not falsely claim those handles remain usable. See [signature handling](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/36172e53-ac81-48fb-b2e3-caa3761b9157), [AEAD failure](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/d3c03e33-7dc7-4d58-8428-0a1484c5c874) and [disconnect cleanup](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/ae543f57-d993-4905-bce0-3cfc446c1fbb).

The encryption-incompatibility case offers AES128-GCM against a server supporting only AES128-CCM. NEGOTIATE legitimately succeeds with `CipherCount=1, Ciphers[0]=0`. An explicitly configured client required-encryption policy then stops locally before authentication. This placement is a declared teaching-policy gate, not an asserted native Windows error status or exact packet timing. It follows [negotiation processing](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/b39f253e-4963-40df-8dff-2f9040ebbeb1), [client zero-cipher handling](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/3b29f3af-86f9-4962-8cf3-43471cb59363) and [client encryption policy](https://learn.microsoft.com/windows-server/storage/file-server/configure-smb-client-require-encryption?tabs=group-policy).
