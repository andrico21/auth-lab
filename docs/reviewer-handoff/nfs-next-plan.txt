NFS authentication and authorization — next-worker plan input
Research date: 2026-10-21. Planning only; no product changes or interoperability test.

Recommendation

Add a separate NFS family covering v3, v4.0, v4.1 and v4.2. Make v4.2 the modern entry point, with version comparisons explaining the earlier flows. NFSv4 does not automatically mean Kerberos, encryption, or authorization. Present five independent decisions: NFS version; RPC caller authentication; RPC message protection; transport protection/host identity; export and filesystem authorization.

Use a small shared fixture engine, not a combinatorial catalog of every version/security setting. Propose twelve core scenarios below, then four bounded advanced follow-ups. Every core scenario includes named failure inputs. All examples remain deterministic synthetic educational fixtures. Linux implementation choices and Windows capabilities must be separately badged from RFC requirements.

Published-version and support matrix

Version | Published reference / status | Authentication requirement versus actual use | Flow differences worth teaching
NFSv3 | RFC 1813, Informational; RFC 2623, Proposed Standard security integration | AUTH_SYS is common, but v3 is not restricted to AUTH_SYS: RPCSEC_GSS/Kerberos is specified. Do not copy the historical DES algorithm choices into a modern fixture. | Separate MOUNTv3 obtains initial filehandle and permitted auth flavors; ordinary NFS procedure calls then carry RPC credentials. No v4 COMPOUND or v4 session.
NFSv4.0 | RFC 7530, Proposed Standard; updates RFC 7931 / RFC 8587 | Both endpoints MUST support RPCSEC_GSS/Kerberos and all krb5, krb5i, krb5p services. This is implementation capability, not a requirement to select Kerberos on every mount. AUTH_SYS remains possible. | Integrated namespace traversal, SECINFO, OPEN/stateid, SETCLIENTID/confirmation. No separate MOUNT protocol. Callback authentication is a separate direction if delegation is shown.
NFSv4.1 | RFC 8881, Proposed Standard, obsoletes RFC 5661 | Both endpoints MUST support krb5 and krb5i; server MUST support krb5p, client SHOULD support it. AUTH_SYS/AUTH_NONE are optional capabilities, not forbidden. | EXCHANGE_ID / CREATE_SESSION / SEQUENCE, optional state-protection policy, backchannel, trunking and pNFS. Session identity is not user authentication.
NFSv4.2 | RFC 7862, Proposed Standard, updated by RFC 8178; v4.1 base semantics retained | No new universal user-authentication mechanism and no automatic TLS. The v4.1 security baseline continues. | New v4.2 features are optional; Labeled NFS and inter-server COPY add conditional security concerns, not mandatory Kerberos delegation or RPCSEC_GSSv3 for every client.

Currentness: the NFS WG document list still identifies draft-ietf-nfsv4-rfc8881bis-11 (2026-09-23), ACL updates and POSIX ACL work as Internet-Drafts. Do not publish their proposed changes as current RFC requirements. No published v4.3 baseline was found. Recheck the RFC Editor status and errata records before implementation and save the actual reference snapshot/commit, rather than a guessed revision hash.

Implementation profiles

- Main interoperable illustration: Linux NFS client/server, explicit vers=3 / 4.0 / 4.1 / 4.2, TCP, fixed hostnames, configured export, and a modern Kerberos GSS mechanism using a pinned supported AES enctype. Record exact kernel, nfs-utils, Kerberos library and optional ktls-utils builds if any native verification is later performed. Kernel configuration affects support; a generic "Linux" label is insufficient for a live capability claim.
- Linux uses userspace context establishment and kernel per-RPC protection. Show rpc.gssd / gssproxy only as optional expanded local components. Keep the application user's credential cache separate from machine credentials used for state management. The currently published kernel documentation says RPCSEC_GSSv3 is not implemented; therefore label v3-of-RPCSEC_GSS illustrations as standards-only unless verified for a different implementation.
- Optional vendor profile: Windows Server 2025 Server for NFS, Linux client, NFSv4.1, Kerberos. Microsoft's current table lists Server for NFS v2/v3/v4.1 and built-in Client for NFS v2/v3. Do not invent Windows NFSv4.2 or a built-in Windows v4.1 client. Current overview documents krb5/krb5i/krb5p, superseding older blog statements about only two flavors. Show AD principal/account mapping and Windows file authorization as a sourced vendor policy boundary.

Core scenario matrix — stable proposed IDs

ID / profile | Visible journey and objects | Required outcome and negative inputs
NFS-01 lab-nfs-v3-auth-sys | MOUNTv3 selected export -> returned filehandle/auth-flavor list -> NFSv3 READ with AUTH_SYS stamp, machine-name, UID, primary GID and supplementary groups -> local export/filesystem checks. | Label identity "client asserted", never "cryptographically verified". Compare ordinary UID success with root_squash mapping UID/GID 0 to configured anonymous IDs, export rejection, UID mismatch and filesystem denial. A mount/filehandle is not proof of subsequent access permission.
NFS-02 lab-nfs-v3-kerberos | Cached user TGT -> TGS exchange for nfs/files.corp.example -> RPCSEC_GSS INIT/optional CONTINUE_INIT -> GSS mutual authentication -> protected NFSv3 READ. MOUNT auth flavor advertises a pseudo-flavor; data RPC uses RPCSEC_GSS flavor 6. | Default krb5i. Failure inputs: absent user credential, wrong service principal/key version, expired ticket, clock skew and failed server proof. No user password or TGT is sent to NFS server; no repeated TGS exchange per READ.
NFS-03 lab-nfs-gss-protection | Three synchronized independent examples of the same authenticated READ with sec=krb5 / krb5i / krb5p; default v4.2, reusable v3 envelope comparison. | Show RPC credential/verifier separately from procedure body. krb5 authenticates RPC without body confidentiality/integrity; krb5i adds body integrity; krb5p wraps body for confidentiality and integrity. A corrupted-body fixture must not claim krb5 detects what it does not protect. Neither krb5p nor its name means whole-IP-packet encryption.
NFS-04 lab-nfs-v40-auth-sys | NFSv4.0 pseudo-root/namespace traversal and one OPEN/READ under configured AUTH_SYS; no MOUNT RPC. | Explicit comparison with NFS-01 proves v4.0 itself has not authenticated the user cryptographically. Preserve file-level policy checks. Include an AUTH_SYS-disallowed export failure.
NFS-05 lab-nfs-v40-kerberos | Full v4.0 path: user GSS context, separately scoped client/state-management identity, SETCLIENTID/SETCLIENTID_CONFIRM as required, namespace traversal, OPEN, krb5p READ, CLOSE. | Keep GSS context handle, clientid, filehandle and stateid distinct. Use supported version-specific operations; do not paste CREATE_SESSION or SEQUENCE into v4.0. Delegations off in the bounded base; if enabled, separately show authenticated callback establishment and failure.
NFS-06 lab-nfs-v41-session-identities | Machine-credential context -> EXCHANGE_ID with an explicitly supported SP4_MACH_CRED profile -> CREATE_SESSION -> separate user GSS context -> SEQUENCE/OPEN/READ. | Differentiate machine state ownership, user authorization and replay-slot sequencing. Machine authentication alone does not authorize Alice's READ. Wrong machine credential cannot take over protected state. Loss/retry must not double-apply a non-idempotent operation; distinguish RPCSEC_GSS sequence window from NFS slot/sequence state.
NFS-07 lab-nfs-wrongsec-discovery | v4.1 namespace crossing under an unacceptable security tuple -> permitted NFS4ERR_WRONGSEC boundary -> SECINFO / supported SECINFO_NO_NAME -> policy-approved stronger tuple -> retry. | Show mechanism OID, QOP and service selection. No silent downgrade. A no-common-allowed-flavor input remains denied. Do not return WRONGSEC from arbitrary operations: use the exact version's allowed operation/error rules. SECINFO_NO_NAME is recommended generally and required for file-layout pNFS, not universally mandatory for every v4.1 server.
NFS-08 lab-nfs-principal-mapping-authorization | Valid Kerberos principal -> explicitly configured local authorization identity/group mapping -> export policy -> file mode/ACL decision. Show owner/owner_group metadata separately from RPC caller credentials. | Named variants: unmapped principal, denied group, read-only export, ACL-denied WRITE and successful READ. NFSv4 owner strings such as alice@id.example are not interchangeable with Kerberos alice@CORP.EXAMPLE, DNS domains or AD forest trusts. An owner-display mapping failure must not automatically be presented as failed cryptographic authentication.
NFS-09 lab-nfs-v42-kerberos-baseline | v4.2 COMPOUND minorversion=2 using the same verified user RPCSEC_GSS path and session machinery, ending in an authorized ordinary READ. | Modern default lesson. Explain that moving 4.1 -> 4.2 adds optional operations, not a new login handshake. Discover optional capability before one optional operation; unsupported operation reports its actual NOTSUPP result, not "authentication failed".
NFS-10 lab-nfs-rpc-tls-auth-sys | v4.2 over TCP: AUTH_TLS discovery -> STARTTLS indication -> TLS1.3+ host authentication -> AUTH_SYS RPC -> export/filesystem checks. Compare explicit xprtsec=tls and mtls profiles; two local users may share one host transport. | TLS does not authenticate Alice or attest her UID. mTLS identifies the client host; root_squash and file policy still apply. Keep outer ciphertext and endpoint-decoded RPC separate. Missing/untrusted client certificate or disallowed host prevents success. No invented HTTPS wrapping or TLS-specific NFS port.
NFS-11 lab-nfs-rpc-tls-required-failure | Fixed strict TLS policy; unsupported AUTH_TLS, wrong server identity, expired/revoked certificate or ALPN mismatch. | Connection/mount failure, no cleartext fallback and no synthetic NFS "wrong password" result. Include a separately labeled opportunistic comparison only if authored explicitly; never silently change the selected policy.
NFS-12 lab-nfs-windows-server-v41 | Linux client -> AD KDC ticket -> Windows Server 2025 NFSv4.1 GSS context -> mapped Windows authorization identity -> share/file policy -> READ. | Pin supported Kerberos flavor and vendor mapping mode. Failures distinguish service key/principal, mapping, share permission and file ACL. No Windows NFSv4.2 claim, no inferred LDAP/Kerberos packet for undocumented internal mapping, no credential forwarding to AD on every READ.

Advanced phase — deliberately bounded, not prerequisites for basic NFS

Advanced follow-up: GSS over TLS | Separate TLS host identities and user GSS authentication on the protected connection. Include RFC 9289 / RFC 9266 tls-exporter channel binding; mismatched binding fails. Do not badge a generic Linux mount as conforming to this combined profile without checking actual channel-binding support. Use a standards illustration if support remains unverified; avoid pretending both layers share keys.
Advanced follow-up: v4.2 Labeled NFS | Capability-gated Labeled NFS: file object security label plus an expressly chosen MAC mode. Show valid user/ordinary ACL but policy-dependent label denial. Limited Server mode stores/transmits labels; it does not enforce full subject-label semantics. Full Mode requires the additional RPCSEC_GSSv3 subject-label assertion capability. No automatic Linux Full Mode support claim.
Advanced follow-up: pNFS file-layout access | Metadata-server authorization -> file layout -> independently authenticated data-server connection/context -> permitted READ. Restrict to the NFS file-layout profile; other storage layouts have different security. A layout/filehandle is not a bearer credential that bypasses the data server's protection. Include wrong data-server principal or incompatible security-policy failure.
Advanced follow-up: trunking identity | A second network path claims matching server owner/scope -> authenticated verification and BIND_CONN_TO_SESSION under the selected state-protection mode -> reuse only after proof. Incorrect server/credential cannot join the session. Do not present matching IP names or equal server-owner strings as sufficient authentication.

Deferred, named extension: inter-server COPY authorization, RFC 7862 section 4.9 / RFC 7861. If later added, show source-read and destination-write authority, partner identity and scoped copy privileges/cleanup. It must not become "forward Alice's password/TGT". RPCSEC_GSSv3 structured privileges are one published conditional design, not universal deployed NFSv4.2 behavior. This is beyond the first teachable release.

Protocol authoring contract

1. Use an explicit state progression: transport available -> host authenticated (if applicable) -> GSS context complete -> user principal verified -> local identity mapped -> export permitted -> operation authorized -> response verified. A received packet, cached ticket, mount, sessionid, stateid or filehandle alone must not set "file access succeeded".
2. RPCSEC_GSS setup uses service program/version with NULL procedure and INIT/CONTINUE_INIT control values; carry GSS tokens in setup body. Include context handle, major/minor status, sequence window and the completion verifier. In the Kerberos profile inspect AP-REQ, AP-REP/server proof and locally derived keys inside the GSS envelope. Choose mutual authentication explicitly. Reuse the existing Kerberos lesson for acquiring a TGT rather than duplicating all AS/PKINIT/FAST flows here.
3. For DATA, show version, gss_proc, seq_num, service, handle and verifier; preserve MIC coverage and body wrapping. Bad verifier, replay/out-of-window and expired/destroyed context are RPC/GSS failures; WRONGSEC is an NFS policy-selection error; ACCESS/ROFS is authorization/filesystem outcome. Do not flatten these into one failure reason.
4. AUTH_SYS is asserted numeric identity plus externally trusted client policy. Root squashing is a Linux export mapping policy, not a login mechanism and not protection against every malicious non-root UID assertion. Distinguish server auth-to-authz mapping from metadata wire-to-local-name mapping. Do not assume idmapd performs Kerberos proof verification.
5. Linux sec= selects RPC security; xprtsec= selects transport policy. Export xprtsec's documented default permits none:tls:mtls when TLS is enabled, whereas client default is kernel-dependent and usually none. Therefore every TLS example must specify policy. Include tlshd availability as a prerequisite, not an authentication actor sending user tickets.
6. RPC-with-TLS requires TLS1.3 or later, authenticated confidential suites, sunrpc ALPN and no 0-RTT. AUTH_TLS is discovery, not a replacement caller credential on subsequent RPCs. Pin TLS packet placement to the current TLS specification and reconcile RFC 9289's historical "ServerHello" ALPN wording with TLS1.3 EncryptedExtensions; record any errata disposition instead of copying an invalid flight. Do not generalize this TCP lesson to RPC/RDMA or QUIC.
7. Keep all secrets, contexts and handles first-class: user/machine TGT and service ticket; server keytab handle; GSS initiator/acceptor keys and context IDs; UID/GID/group mapping; export and file ACL; TLS endpoint keys/certificates; session and slot state; filehandle/stateid; pNFS layout when selected. Author wire, decoded and local representations independently; never export private keys, raw user passwords or a TGT to the NFS server.

Acceptance / usability gates

- Offer version, sec and xprtsec as separate visible fields. Show a compact protection table: claimed/verified user; authenticated host(s); body integrity; body confidentiality; visible outer RPC metadata. Mark standards-required support, configured policy and verified implementation capability separately.
- Default to NFS-09. Version comparisons use aligned milestones and highlight only real differences. Explain MOUNT versus namespace traversal, GSS context versus NFS session, root_squash versus ACLs, and user versus machine identity in plain language.
- Independently assert endpoint permissions at receipt/unwrap, ticket/context lifetime, exact MIC/body scope, no early authorization, version-correct operations, malformed and stale proof handling, bounded retry effects, rewind/reset and exact-history representation preservation. Test named failure inputs at their first detector boundary, not merely final text.
- Keep the first release offline; real protocol libraries or privileged mounts are not required. Any later native interoperability evidence must name its builds and demonstrate one representative supported combination before promoting a vendor capability badge.
