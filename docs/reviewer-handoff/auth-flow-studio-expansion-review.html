F2 — P2 — HTTP authentication messages lack a valid response grouping/continuation boundary. File: src/windows-auth-lab.js:192, 196–198, 347–354, 369, 387–389. Scenarios: W06; also W20/W22/W23 HTTP-CredSSP profiles. W19 shares the non-CredSSP AP-REP branch. Observed: W06 wire order is C→S ap-request, S→C ap-reply, S→C result. In WinRM CredSSP, ap-reply and server-binding are independently HTTP-framed H→C messages without an intervening C request. No declared macro says these are inner records within one HTTP response. Expected: associate final Kerberos token and application response with the correct HTTP response, and distinguish receipt from client mutual-proof acceptance/use. RFC4559 §5 puts final server authentication data in WWW-Authenticate on the final response containing the body. Multiple inner CredSSP TLS/TSRequest messages can share one carrier response, but must be explicitly grouped or have a sourced continuation exchange; they are not independent unsolicited HTTP responses. Fix/test: author carrier request/response identifiers or explicit compound carrier events. Retain inner protocol/object projections without duplicating HTTP response events. Assert every noninformational HTTP response belongs to an outstanding request and that final data is unusable until mutual verification. Primary: https://www.rfc-editor.org/rfc/rfc4559.html#section-5 Primary: https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-wsmv/b37174e4-00cb-4830-930f-97809d3302da

N-01 — P2 — RFC 9190 exporter uses the wrong context Location: src/network-access-lab.js:68 and :369–370. Scenarios: NET-E01 lab-net-eap-tls13-wired; NET-E04 lab-net-eap-policy-denied; NET-T01 lab-net-radius-udp-radsec (both independent transactions); NET-P01 lab-net-radius-proxy-realm; NET-W01 lab-net-enterprise-wifi-eap.

Actual: the field help and both endpoint derivation steps teach TLS-Exporter("EXPORTER_EAP_TLS_Key_Material", empty context, 128). This occurs in twelve exporter events across five default presets. RFC 9190 section 2.3 requires the context to be the one-octet EAP Type value 0x0D. Empty context produces different key material, so the formula is incorrect even though the examples are symbolic. The 64-byte MSK / 64-byte EMSK split is correct.

Reproduce: choose Wired 802.1X EAP-TLS 1.3 and inspect the Server exporter derivation and Peer exporter derivation payloads; each explicitly says "context empty". Programmatically inspect model.steps() for the :server-export / :peer-export suffixes, including :udp: and :radsec: scoped copies.

Expected/fix: author the byte-valued context Type = 0x0D consistently in the canonical fields, field help, local object provenance and any derived documentation. Keep this separate from TLS 1.2's PRF formula. If Method-Id / EAP Session-Id are taught, use their distinct exporter label and Type || Method-Id formula. Add an independent assertion for label, context bytes, length and MSK/EMSK ranges; the existing tests only verify causal state and do not check this formula.

Primary source: https://www.rfc-editor.org/rfc/rfc9190.html#section-2.3 Retrieved evidence: turn293view2, lines 485–497. It specifies Type = 0x0D and uses Type as both exporter contexts.
