Non-negotiable invariants

  1. No receipt before delivery. A visual animation fraction must not create a receiver holding or knowledge before the canonical message receipt. Local verification and authorization must not be inferred from animation completion alone.
  2. Local intent is not remote state. A cancel, timeout or rejected request cannot delete a remote session or credential without the relevant protocol event. Remote results can remain unknown when an acknowledgement is lost.
  3. Encrypted on the wire does not mean unreadable to the endpoint. Give legitimate recipients their narrow, explicit decoded-field permissions. Keep nested representations separate: an EAP relay may carry records it cannot decrypt; a CredSSP password recipient can recover delegated credentials.
  4. Never broaden shared reader defaults to repair one scenario. Author field-level permissions per profile. Retain exact receipt occurrences even when a transient request copy is acquired and released within the same canonical event.
  5. Wire and local values remain distinct. Do not replace ciphertext, authenticators or public exchange values with selected decoded secrets in an exact-history projection. Expose “Wire”, “Decoded by this actor” and “Local derivation” where relevant.
  6. Protocol completion is explicit. A verified identity is not yet authorization; an authorization response is not necessarily a live network or RDP session; a PAKE shared value is not yet a confirmed application key.
  7. History is not current possession. Rewind, expiry, release and context replacement retain clearly historical entries without granting current knowledge. Exact replay follows the selected generation and occurrence.
  8. Illustrated cryptography is honest. Use published test vectors when showing real derived bytes, or clearly labeled symbolic values with internally consistent relationships. Do not mix real-looking bytes with impossible derivations or describe placeholders as a captured exchange.
  9. Trust crossings are authored. NTLM pass-through, RADIUS proxying and Kerberos referrals have different routing and protection rules. Do not reuse one family’s arrows, session keys or trust semantics merely because each spans two domains.
  10. Replay is one history. All view modes, speed settings, seeks and internals folding project the same completed prefix and active milestone. A UI-only change cannot execute authentication or mutate protocol state.

Use synthetic principals such as alice@CORP.EXAMPLE, reserved example hostnames, fake certificates and conspicuously non-production credentials. No artifact should ask a learner to paste a real password, ticket or private key.

W2. NTLM, Negotiate and trust correctness

Implement W01–W08 first. Show local password-derived credential material, fresh server/client challenges, response blob, NT proof, session-key derivation and verification as different objects. An NT hash is neither the transmitted challenge response nor a reusable Kerberos ticket. Expose sensitive local derivation only to its owner’s inspection view. Use the authoritative NTLMv2 calculation and validation rules; do not use digest-looking placeholder strings as evidence of correct computation.

For domain accounts, S sends the challenge/response validation request through Netlogon, receives validation/session-key information, and independently applies application policy. D is acting as account validator, not processing AS-REQ/TGS-REQ. For local accounts, the local authority performs validation. The MS-APDS pass-through example anchors the separation. Display raw NTLM security tokens independently from their application envelope; select and document one carrier before claiming its concrete HTTP/SMB wire details.

W03 must draw the server’s secure channel to DR and the distinct trusted-domain secure channel toward D. Its direct-trust fixture is justified by MS-NRPC §1.3.2; do not copy Kerberos referral arrows or invent end-user KDC contacts. Preserve domain-qualified identities, trust direction, selected route and returned authorization data. W04 must declare its precise failure and current pass-through validation assumptions. A direct-trust example must not imply arbitrary forest transitivity.

Track SPNEGO’s selected mechanism and integrity state separately from its underlying mechanism. Pin MIC, target-name and channel-binding behavior to the chosen profile. HTTPS, an NTLM MIC, extended protection and application signing are different protections; none may silently stand in for another. A field named LmChallengeResponse does not alone establish use of legacy LM authentication: reproduce the selected NTLMv2 profile’s actual field rules. No exploit, relay or credential-extraction tooling is required.

W3. CredSSP credential and binding boundaries

Implement W09–W13 next, reusing verified mechanism models. CredSSP establishes its TLS channel, exchanges mechanism tokens in TSRequest.negoTokens, verifies directional server-public-key bindings, and transfers protected authInfo. Pin modern v6 behavior: the binding input includes the direction-specific magic string with its terminating NUL, the 32-byte client nonce and the TLS certificate’s encoded SubjectPublicKey. Do not substitute the entire certificate, SPKI wrapper, thumbprint, or a generic “TLS established” flag. The two directions produce different proofs. Follow MS-CSSP processing rules: when the client sends its last mechanism token, the TSRequest must carry both negoTokens and pubKeyAuth. Make the combined-message requirement an explicit fixture assertion; any expanded explanatory substeps remain projections of that one wire message.

Give TLS traffic keys, mechanism session/subsession keys, public-key-binding values and credential structures separate identities and readers. Credential receipt belongs to the completed authInfo delivery and successful unwrap at H, not the preceding local construction/send or the end of SPNEGO. Ordinary password CredSSP intentionally lets H recover delegated password credentials; encrypted transport does not mean H cannot read them. Its delegation contract differs from constrained delegation. Smart-card credential types may be explained but are not silently substituted into this password fixture.

W4. Three RDP modes, three different credential stories

Implement W14–W18 after the CredSSP engine. Author RDP’s requested security protocols/mode and the server’s advertised selection/support separately using RDP_NEG_REQ and RDP_NEG_RSP. Restricted Admin allows empty TSPasswordCreds; this is not equivalent to omitting authInfo or pretending ordinary password delegation occurred. Remote Credential Guard uses the redirected-credential branch: TSCredentials.credType=6 with TSRemoteGuardCreds, according to the credential-type definition.

The comparison must show ordinary RDP’s delegated user credentials, Restricted Admin’s downstream host identity, and Remote Credential Guard’s redirected user authentication. Remote Credential Guard requires Kerberos for the RDP connection and does not allow NTLM fallback; user secrets stay client-side while the remote host can still hold service tickets. It is a direct-RDP scenario, not an RD Gateway or generic WinRM feature. Ground these limits in Microsoft’s profile documentation. Before implementing W16, map the necessary MS-RDPEAR exchanges and opaque package buffers to their actual owners; do not render them as a password, copied TGT or ordinary credential blob.

Remote Credential Guard still sends protected authInfo, containing logonCred and optional supplementalCreds. Each packageName/credBuffer pair has a package/OS-specific buffer; preserve it as opaque unless verified decoding is available. Model the continuing authentication redirection using MS-RDPEAR. Its general package capabilities do not authorize an initial RCG NTLM fallback. Restricted Admin’s downstream machine identity does not mean the entire interactive session executes as the machine account. At disconnect, close the redirection channel separately from any already-issued service ticket or independently established resource session.

For all modes, separate mechanism acceptance, protected credential/redirected-context receipt, remote-logon authorization, RDP session readiness and downstream resource access. If HYBRID_EX is selected, include its early authorization result at the correct boundary. Mode-support rejection and logon-policy denial remain visibly different outcomes.

W5. WinRM second hop and transport layering

Implement W19–W23 as required applied flows. Use a downstream file service with an explicitly authored authentication and ACL policy. The initial WinRM session never implies possession of the user’s reusable credentials or permission on R. Microsoft’s second-hop guidance explains both ordinary failure and CredSSP’s credential availability on H; show this custody change directly.

WinRM supports explicit-credential CredSSP through either an HTTP or HTTPS listener, with client/service enablement and target delegation policy. Therefore model outer HTTP versus HTTPS separately from CredSSP’s inner TLS. Label and trace each channel’s endpoints, keys and certificate roles. An HTTP listener does not remove the inner TLS; an HTTPS listener does not replace the CredSSP handshake/binding. Microsoft’s WinRM multi-hop documentation establishes these configurations. Verify the exact encapsulation and message-protection rules before drawing wire records; do not assume a single shared TLS context or that every certificate authenticates the same layer.

W6. Object/state assertions and acceptance tests

  • Objects: distinct challenge/response instances, local password/hash-derived handles, NTLM session keys, Netlogon channel identities, Kerberos tickets/keys, SPNEGO context, inner/outer TLS keys, nonce/binding proofs, protected wire authInfo, recovered credentials or redirected handles, Windows logon context, RDP/WinRM session and downstream authorization result.   • Knowledge: a service inspecting a received NTLM response cannot read the user’s raw NT hash; D’s account record is not forwarded to S. Protected wire views remain opaque.   • Independent state: transport ready, mechanism complete, binding verified, export allowed, credentials received, logon authorized, session established and resource authorized must be separate. A later denial cannot rewind earlier disclosure; an earlier authenticated session survives an unrelated downstream access denial.
  • Protocol tests: use published NTLMv2 vectors where applicable; check v6 direction strings, terminating NUL, nonce, exact public-key encoding, mismatched binding and combined-message handling.   • Player tests: before/at/after every receive and validation boundary, full/link/field/exact-object replay must produce identical canonical state. Rewind, reset, switching profiles, collapsed internals and historical selection must not leak holdings from another mode or create duplicate credential receipt.
  • UX/evidence: test all 23 catalog entries, keyboard selection, focus recovery, small-screen inventory and explanatory labels. Default to the user journey; make token/ASN.1 details expandable.
