Local accounts

  • Applies to: ✅ Windows 11, ✅ Windows 10, ✅ Windows Server 2025, ✅ Windows Server 2022, ✅ Windows Server 2019, ✅ Windows Server 2016

In this article

This article describes the default local user and system accounts for Windows operating systems, and describes how to manage them.

Local accounts (user accounts and system accounts) are security principals that're used to manage user and system access to the resources on a device. Local user and system accounts are defined locally on a device, and the device is the security authority. These accounts have rights and permissions only on that device.

Default local user accounts

The default local user accounts are built-in local user accounts that the operating system creates automatically when it installs. You can't remove or delete the default local user accounts. Default local user accounts have rights and permissions to manage access to the local device's resources. They don't provide access to network resources.

To manage a computer's local user accounts, use the Computer Management Microsoft Management Console (MMC). Computer Management is a collection of administrative tools that you can use to manage a local or remote device. The default local user accounts, and the local user accounts that you create, are located in the Local Users and Groups\Users folder in Computer Management.

The following sections describe the default local user accounts.

Administrator

The default local Administrator account is a user account that's intended for system administration. Every computer is a security authority and has an Administrator account (the account security identifier (SID) is S-1-5-<SecurityAuthorityName>-500, and its display name is Administrator). The Administrator account is the first account that's created during the Windows installation.

The Administrator account has full control of the files, directories, services, and other resources on the local device. The Administrator account can create other local users, assign user rights, and assign permissions. The Administrator account can take control of local resources at any time by changing the user rights and permissions.

You can't delete or lock out the default Administrator account. However, you can rename or disable it.

Windows setup disables the built-in Administrator account and creates another local account that is a member of the Administrators group.

Members of the Administrators groups can run apps by using elevated permissions without using the Run as Administrator command.

Account group membership

By default, the Administrator account is a member of the Administrators group. It's a best practice to limit the number of users in the Administrators group, because members of the Administrators group have Full Control permissions on the device.

You can't remove the Administrator account from the Administrators group.

Security considerations

The Administrator account is known to exist on many versions of the Windows operating system. Therefore, it's a best practice to disable the Administrator account when possible to make it more difficult for malicious users to gain access to the server or client computer.

You can rename the Administrator account. However, a renamed Administrator account continues to use the same automatically-assigned SID, which malicious users can be discover. For more information about how to rename or disable a user account, see Disable or activate a local user account and Rename a local user account.

As a security best practice, use your local (non-Administrator) account to sign in and then use Run as administrator to accomplish tasks that require a higher level of rights or permissions than a standard user account. Don't use the Administrator account to sign in to your computer unless it's necessary. For more information, see Run a program with administrative credentials.

You can use Group Policy to automatically control the use of the local Administrators group. For more information about Group Policy, see Group Policy Overview.

Important

  • You can't use a blank password for the Administrator account.
  • Even when the Administrator account is disabled, you can still use it to gain access to a computer if you start it in safe mode. The following rules apply when you sign in to a computer in safe mode:
    • When networking is enabled, you can use a domain user account that is member of the administrators group.
    • When one other member of the local administrators group is enabled, you can use that member account.
    • If no other account is enabled, safe mode automatically enables the Administrator account. When you start the computer in normal mode instead of safe mode, the Administrator account is disabled.

Guest

Occasional or one-time users who don't have an account on the device can use the Guest account to temporarily sign in to the local device. The account security identifier (SID) is S-1-5-21-<SecurityAuthorityName>-501, and its display name is Guest. The Guest account has limited user rights and permissions. By default, the Guest account is disabled and has a blank password. Because the Guest account can provide anonymous access, it's considered a security risk. For this reason, it's a best practice to leave the Guest account disabled, unless its use is necessary.

Guest account group membership

By default, the Guest account is the only member of the default Guests group (the group SID is S-1-5-32-546). This group has the rights and permissions that the Guest account needs to sign in to a device.

Guest account security considerations

When enabling the Guest account, only grant limited rights and permissions. For security reasons, don't use the Guest account over the network, and don't allow other computers to access it.

In addition, the Guest account shouldn't be able to view the event logs. After you enable the Guest account, it's a best practice to monitor the Guest account frequently to make sure that other users can't use services and other resources. Such resources include those that a previous user left available unintentionally.

DefaultAccount

The DefaultAccount account, also known as the Default System Managed Account (DSMA), is a well-known user account type. DSMA can run processes that are either multi-user aware or user-agnostic.

The DSMA is disabled by default on the desktop editions and on the Server operating systems with the desktop experience.

The DSMA has a well-known RID of 503. The security identifier (SID) of the DSMA thus has a well-known SID in the following format: S-1-5-21-<SecurityAuthorityName>-503.

The DSMA is a member of the well-known System Managed Accounts Group, which has a well-known SID of S-1-5-32-581.

The DSMA alias can be granted access to resources during offline staging even before the account itself is created. The account and the group are created within the Security Accounts Manager (SAM) the first time the computer starts.

How Windows uses the DSMA

From a permission perspective, the DSMA is a standard user account.

Multi-user-manifested-apps (MUMA apps) need the DSMA to run on Windows-based devices. MUMA apps run all the time and react to users signing in and signing out of the device. Unlike Windows Desktop, where apps run in context of the user and get terminated when the user signs off, MUMA apps run by using the DSMA.

MUMA apps function in shared session SKUs such as Xbox. For example, the Xbox shell is a MUMA app. Today, Xbox automatically signs in as Guest account and all apps run in this context. All the apps are multi-user-aware and respond to events fired by user manager. The apps run as the Guest account.

In the converged user model, the multi-user-aware apps and multi-user-aware brokers run in a different context from that of the users. For this purpose, the system creates the DSMA.

How the DSMA is created on domain controllers (DCs)

If the domain was created by using DCs that run Windows Server 2016-or a later Windows Server version, the DSMA exists on all DCs in the domain as a local account. It resides in the same mini account database as the Administrator of the Directory Service Restore Mode (DSRM).

Recommendations for managing the DSMA

Microsoft doesn't recommend changing the default configuration, where the account is disabled. There's no security risk with having the account in the disabled state. Changing the default configuration could hinder future scenarios that rely on this account.

WDAGUtilityAccount

The WDAGUtilityAccount is a predefined local account that Windows Defender Application Guard uses. The account has a well-known SID value, S-1-5-21-<SecurityAuthorityName>-504. By default, this account doesn't belong to any groups.

WSIAccount

The WSIAccount is a predefined local account that's introduced in Windows 11. Windows uses this account for web-related activities that start from the lock or sign-in screen. Such activities include accessing credential provider web pages for password reset or web-based authentication. It has a well-known SID value, S-1-5-21-<SecurityAuthorityName>-1001. By default, this account belongs to the Users group.

Default local system accounts

SYSTEM

The SYSTEM account is used by the operating system and by services that run under Windows. It has a well-known SID value, S-1-5-18. There are many services and processes in the Windows operating system that need the capability to sign in internally, such as during a Windows installation. The SYSTEM account was designed for that purpose, and Windows manages the SYSTEM account's user rights. It's an internal account that doesn't show up in User Manager, and it can't be added to any groups.

On the other hand, the SYSTEM account does appear on an NTFS file system volume in File Manager in the Permissions portion of the Security menu. By default, the SYSTEM account is granted Full Control permissions to all files on an NTFS volume. In this context, the SYSTEM account has the same functional rights and permissions as the Administrator account.

Note

To grant the account Administrators group file permissions does not implicitly give permission to the SYSTEM account. The SYSTEM account's permissions can be removed from a file, but we do not recommend removing them.

NETWORK SERVICE

The NETWORK SERVICE account is a predefined local account the service control manager (SCM) uses. The account has a well-known SID value, S-1-5-20. A service that runs in the context of the NETWORK SERVICE account presents the computer's credentials to remote servers. For more information, see NetworkService Account.

LOCAL SERVICE

The LOCAL SERVICE account is a predefined local account that the SCM uses. The account has a well-known SID value, S-1-5-19. It has minimum privileges on the local computer and presents anonymous credentials on the network. For more information, see LocalService Account.

HelpAssistant

The HelpAssistant account is a default local account that's only enabled during Remote Assistance sessions. when no Remote Assistance requests are pending, the HelpAssistant account is automatically disabled.

HelpAssistant is the primary account that's used to establish a Remote Assistance session. The Remote Assistance session connects to another Windows-based computer, and it's initiated by invitation. To solicit remote assistance, a user sends an invitation from their computer, through e-mail or as a file, to a person who can provide assistance. After the user's invitation for a Remote Assistance session is accepted, the default HelpAssistant account is automatically created to give the person who provides assistance limited access to the computer. The Remote Desktop Help Session Manager service manages the HelpAssistant account.

HelpAssistant account security considerations

The SIDs that pertain to the default HelpAssistant account include the following values:

  • SID: S-1-5-13, display name Terminal Server User. This group includes all users who sign in to a server while Remote Desktop Services is enabled.
  • SID: S-1-5-14, display name Remote Interactive Logon. This group includes all users who connect to the computer by using a remote desktop connection. This group is a subset of the Interactive group. Access tokens that contain the Remote Interactive Logon SID also contain the Interactive SID.

Note

These SIDs are classified as "Well-known" SIDs. For more information, see the Well-known SIDs section of Security identifiers.

For the Windows Server operating system, Remote Assistance is an optional component that isn't installed by default. You must install Remote Assistance before it can be used.

How to manage local user accounts

As described earlier, the default local user accounts, and the local user accounts you create, reside in the Local Users and Groups\Users folder in Computer Management. For more information about creating and managing local user accounts, see Manage Local Users.

To limit the ability of local users and groups to perform certain actions, you can use Local Users and Groups to assign rights and permissions on only the local computer. A right authorizes a user to perform certain actions on a device, such as backing up files and folders or shutting down a computer. An access permission is a rule that is associated with an object, usually a file, folder, or printer. It regulates which users can have access to an object on the server and in what manner.

You can't use Local Users and Groups on a DC to manage accounts on the DC. You can use Local Users and Groups on a DC to target remote computers that aren't DCs, if your network allows remote administration.

You can also manage local users by using NET.EXE USER and manage local groups by using NET.EXE LOCALGROUP, or by using the Microsoft.PowerShell.LocalAccounts Module cmdlets in Windows PowerShell.

Protect default workstation accounts while the accounts are in use

In Windows the Local Security Authority SubSystem (LSASS) process handles all user and system sessions and credentials. To isolate and protect these credentials, follow these steps:

  • For all computer roles (e.g. workstations and servers), configure LSASS to be a protected processes light (PPL) process. For more information and instructions, see Configure added LSA protection.

  • For workstations, make sure that Credential Guard is running to further isolate active credentials and secrets are isolated. Depending on your computer configuration, Credential Guard is typically active by default on current versions of Windows. For more information about using Credential Guard, see the following articles:

    • Credential Guard overview
    • Configure Credential Guard
    • How Credential Guard works

Restrict and protect local accounts that have administrative rights

You can use many approaches to prevent malicious users from using stolen credentials such as a stolen password or password hash, for a local account on one computer from being used to authenticate and use administrative rights and permission on another computer. This type of attack is referred to as lateral movement.

The simplest approach is to sign in to your computer with a standard user account and then use that account for administrative tasks, instead of using the Administrator account. For example, use a standard account to browse the internet, send email, or use a word processor. When you want to perform administrative tasks such as installing a new program or changing a setting that affects other users, you don't have to switch to an Administrator account. You can use User Account Control (UAC) to prompt you for permission or an administrator password before performing the task, as described in the next section.

Other approaches that you can use to restrict and protect user accounts that have administrative rights include the following steps:

  • Enforce local account restrictions for remote access
  • Deny the network logon access right to all local Administrator accounts
  • Create unique passwords for local accounts that have administrative rights

The following sections describe each of these approaches.

Enforce local account restrictions for remote access

User Account Control (UAC) is a security feature that informs you when a program makes a change that requires administrative permissions. UAC works by adjusting the permission level of your user account. By default, UAC is set to notify you when applications try to make changes to your computer, but you can change when UAC notifies you.

UAC makes it possible for an account that has administrative rights to be treated as a standard user nonadministrator account until full rights, also called elevation, is requested and approved. For example, UAC lets an administrator enter credentials during a nonadministrator's user session to perform occasional administrative tasks without having to switch users, sign out, or use the Run as command.

In addition, UAC can require administrators to specifically approve applications that make system-wide changes before those applications are granted permission to run, even in the administrator's user session.

For example, a default feature of UAC is shown when a local account signs in from a remote computer by using Network logon (for example, by using NET.EXE USE). In this instance, it's issued a standard user token with no administrative rights, but without the ability to request or receive elevation. Consequently, local accounts that sign in by using Network logon can't access administrative shares such as C$, or ADMIN$, or perform any remote administration.

For more information about UAC, see User Account Control.

The following table shows the Group Policy and registry settings that enforce local account restrictions for remote access.

No. Setting Detailed Description
Policy location Computer Configuration\Windows Settings\Security Settings\Local Policies\Security Options
1 Policy name User Account Control: Admin Approval Mode for the Built-in Administrator account
Policy setting Enabled
2 Policy location Computer Configuration\Windows Settings\Security Settings\Local Policies\Security Options
Policy name User Account Control: Run all administrators in Admin Approval Mode
Policy setting Enabled
3 Registry subkey HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System
Registry value name LocalAccountTokenFilterPolicy
Registry value type DWORD
Registry value data 0

Note

You can also enforce the default local account restrictions by using the custom ADMX in Security Templates. For more information, see Define Security Templates By Using the Security Templates Snap-In.

To enforce local account restrictions for remote access

  1. Start the Group Policy Management Console (GPMC).

  2. In the console tree, navigate to Forest: ForestName > Domains > DomainName, where ForestName is the name of the forest, and DomainName is the name of the domain where you want to configure the Group Policy Object (GPO).

  3. In the console tree, right-click Group Policy Objects, and then select New

  4. In the New GPO dialog box, type a name for the new GPO, and then select OK. Use the GPO name to indicate that the GPO restricts local administrator rights to a single computer.

  5. In the details pane, right-click the new GPO, and then select Edit.

  6. To enable and configure UAC for the default Administrator account, follow these steps:

    1. In the Group Policy Management Editor, navigate to Computer Configuration > Policies > Windows Settings > Security Settings > Local Policies > Security Options.
    2. In the details pane, right-click User Account Control: Run all administrators in Admin Approval Mode, and then select Properties.
    3. Select Define this policy setting, select Enabled, and then select OK.
    4. Right-click User Account Control: Admin Approval Mode for the Built-in Administrator account, and then select Properties.
    5. Select Define this policy setting, select Enabled, and then select OK.

  7. To apply local account restrictions for domain members to network interfaces, follow these steps:

    1. In GPMC, navigate to the domain where you want to apply UAC settings to the domain members.
    2. Create a new GPO, or select an existing GPO that matches the purpose.
    3. Open the GPO for editing.
    4. In Group Policy Management Editor, navigate to Computer Configuration > Preferences > Windows Settings > Registry.
    5. Right-click Registry, and then select New > Registry Item.
    6. In the New Registry Properties dialog box, on the General tab, change the setting in the Action box to Replace
    7. Make sure that the Hive box is set to HKEY_LOCAL_MACHINE
    8. Next to Key Path, select ..., and then select the following subkey: HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System
    9. Select Select.
    10. In the Value name box, type LocalAccountTokenFilterPolicy.
    11. In the Value type box, from the drop-down list, select REG_DWORD.
    12. In the Value data box, type 0, and then select OK.

  8. To link the GPO to the appropriate organizational unit (OU), follow these steps:

    1. In GPMC, navigate to Forest: ForestName > Domains > DomainName > OUName, where ForestName is the name of the forest, DomainName is the name of the domain, and OUName is the name of the OU that contains the members that you want to manage. In this case, the OU contains the workstations whose local accounts you want to restrict.
    2. Right-click OUName, and then select Link an existing GPO.
    3. Select the GPO that you created, and then select OK.

  9. Update the local policy on each of the workstations in the OU. For example, in a Command Prompt window, run gpupdate /force /target:computer.

  10. Test the functionality of enterprise applications on the workstations in that OU, and resolve any issues that the new policy causes.

  11. Link the GPO to all other OUs that contain workstations

  12. Link the GPO to all other OUs that contain servers

Deny the network logon access right to all local Administrator accounts

Denying local accounts the ability to sign in over a network connection (network logon) can help prevent a malicious attacker from reusing a local account password hash. This procedure helps to prevent lateral movement by making sure that attackers can't use stolen credentials for local accounts from a compromised operating system to compromise other computers that use the same credentials.

Note

To perform this procedure, you must first identify the name of the local, default Administrator account, which might not be the default user name "Administrator", and any other accounts that are members of the local Administrators group.

The following table shows the Group Policy settings that deny the network logon right for all local Administrator accounts.

No. Setting Detailed Description
Policy location Computer Configuration\Windows Settings\Security Settings\Local Policies\User Rights Assignment
1 Policy name Deny access to this computer from the network
Policy setting Local account and member of Administrators group
2 Policy location Computer Configuration\Windows Settings\Security Settings\Local Policies\User Rights Assignment
Policy name Deny log on through Remote Desktop Services
Policy setting Local account and member of Administrators group

To deny the network logon right to all local administrator accounts

  1. Start GPMC, and then navigate to Forest: ForestName > Domains > DomainName, where ForestName is the name of the forest, and DomainName is the name of the domain where you want to configure the GPO.

  2. In the console tree, right-click Group Policy Objects, and then select New

  3. In the New GPO dialog box, type a name for the new GPO, and then select OK. Use the GPO name to indicate that the GPO restricts the local administrative accounts from interactively signing in to the computer.

  4. In the details pane, right-click the new GPO, and then select Edit.

  5. To configure the user rights to deny the network logon right for administrative local accounts, follow these steps:

    1. In the Group Policy Management Editor, navigate to Computer Configuration > Policies > Windows Settings > Security Settings > Local Policies > User Rights Assignment.
    2. In the details pane, right-click Deny access to this computer from the network, and then select Properties.
    3. Select Define these policy settings, and then select Add User or Group.
    4. Type Local account and member of Administrators group, and then select OK twice.

  6. To configure the user rights to deny the Remote Desktop (Remote Interactive) logon right for administrative local accounts, follow these steps:

    1. In the Group Policy Management Editor, still in User Rights Assignment, right-click Deny log on through Remote Desktop Services, and then select Properties.
    2. Select Define these policy settings, and then select Add User or Group.
    3. Type Local account and member of Administrators group, and then select OK twice.

  7. To link the GPO to the appropriate organizational unit (OU), follow these steps:

    1. In GPMC, navigate to Forest: ForestName > Domains > DomainName > OUName, where ForestName is the name of the forest, DomainName is the name of the domain, and OUName is the name of the OU that contains the members that you want to manage. In this case, the OU contains the workstations whose local accounts you want to restrict.
    2. Right-click OUName, and then select Link an existing GPO.
    3. Select the GPO that you created, and then select OK.

  8. Update the local policy on each of the workstations in the OU. For example, in a Command Prompt window, run gpupdate /force /target:computer.

  9. Test the functionality of enterprise applications on the workstations in that OU, and resolve any issues that the new policy causes.

  10. Create links to all other OUs that contain workstations

  11. Create links to all other OUs that contain servers

Note

If the user name of the default Administrator account is different on workstations and servers, you might have to create separate GPOs for workstations and servers.

Create unique passwords for local accounts that have administrative rights

Passwords should be unique per individual account. While that's typically enforced for individual user accounts, many organizations have identical passwords for common local accounts, such as the default Administrator account or local accounts that the organization uses during operating system deployments.

Passwords that are left unchanged or changed synchronously to keep them identical add a significant risk for organizations. Randomizing the passwords mitigates "pass-the-hash" attacks by using different passwords for local accounts. Randomized passwords hamper the ability of malicious users to use password hashes of those accounts to compromise other computers.

You can use any of the following methods to randomize passwords. The methods are listed in order of preference:

  • Configuring Local Administrator Password Solution (LAPS) to accomplish this task.
  • Purchasing and implementing an enterprise tool to accomplish this task. These tools are typically referred to as "privileged password management" tools.
  • Creating and implementing a custom script or solution to randomize local account passwords.
