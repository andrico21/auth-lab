1. Model conversation failure as PAM_AUTHTOK_ERR, not PAM_CONV_ERR — P2, confidence 0.92
File: src/pam-foundations-lab.js, line 71
Body: PAM01/conversation-failure injects pam_unix.so:authenticate = PAM_CONV_ERR and the independent ledgers/test expect the pam_authenticate aggregate to be PAM_CONV_ERR. The selected afs-login stack is auth required pam_unix.so. Pinned pam_unix_auth.c:152-166 calls pam_get_authtok for the password; pinned pam_get_authtok.c:176-187 returns PAM_AUTHTOK_ERR whenever the prompt/conversation result is not PAM_SUCCESS. pam_start already stores the user in the handle and pam_get_user returns it (pinned pam_start.c/pam_item.c), so the failing callback here is the password prompt, not the username prompt. The conversation callback itself still returns PAM_CONV_ERR, but the module return and the required control aggregate are PAM_AUTHTOK_ERR. Impact: the case, dispatch-expectations, lifecycle-expectations, case-ledger firstDetection/expectedAPISequence and the test at tests/pam-foundations.test.mjs:59 all teach the wrong PAM result.
Smallest fix: change the line-71 input to "PAM_AUTHTOK_ERR" and update those expectation ledgers/test while keeping the conversation-status object at PAM_CONV_ERR.

2. Tag delete-credentials PAM call with DELETE_CRED and a distinct aggregate — P2, confidence 0.87
File: src/pam-existing-integration.js, lines 5-6
Body: lab-llog01 maps the delete-credentials event to "setcred" (line 6). The wrapper therefore calls pamEvaluate(..."setcred") and every trace row inherits PAM_API_PHASES.setcred.flags = PAM_ESTABLISH_CRED; the event title and the selected application action are PAM_DELETE_CRED after close (S34; S28 setcred cached-chain branch). The same wrapper also pushes workstation.pamResults.setcred at line 55, overwriting the earlier establish return instead of recording a delete result. The foundation lab already models the split correctly: phase("setcred","delete") dispatches with PAM_DELETE_CRED and returned(...,"delete") writes pamResults.setcred-delete. Impact: a consumer cannot distinguish credential establishment from cleanup, and the delete event's module metadata says ESTABLISH.
Smallest fix: for key "delete-credentials", force the evaluated rows and step.pamEvaluation flags to PAM_DELETE_CRED and publish the status under pamResults.setcred-delete, leaving the establish aggregate untouched.

3. Record sudo setcred aggregate separately from open session — P2, confidence 0.80
File: src/pam-existing-integration.js, lines 48-55
Body: lab-lelev01 maps pam-session to "open" (line 10); the special case computes a real pamEvaluate(service,"setcred") with the auth cache and prepends its trace, but then discards credentials.status. step.pamAggregate and the only pamResults effect use the open evaluation. Consequently workstation.pamResults.setcred is never written for the sudo case even though the selected profile includes auth then account/setcred/session (S34; S28 has separate setcred and open-session dispatch switch cases). The active step.pamEvaluation is the setcred row while the aggregate is the open result, so the API boundary is ambiguous. Current variants make setcred succeed, so the defect is the missing/ambiguous aggregate rather than a wrong value.
Smallest fix: retain credentials.status and publish it as pamResults.setcred in addition to the open evaluation's pamResults.open, or emit a separate setcred-return boundary before the open return.

5. Do not publish null pamResults.authenticate from rootok slice — P3, confidence 0.82
File: src/pam-existing-integration.js, lines 41-45
Body: For lab-lelev02 with a configured rootok, the wrapper filters the authenticate trace to the pam_rootok row and deliberately sets evaluation.status = null (lines 41-45), but line 55 unconditionally puts workstation.pamResults.authenticate = evaluation.status. No pam_authenticate aggregate exists at the rootok event; the real su-auth evaluation follows. The canonical path is documented as an API return, so the rootok prefix exposes a null aggregate that can be rendered as a result. Variants where rootok is configured but the real UID is non-root (for example setuid-not-real-root) hit this path.
Smallest fix: skip the pamResults put when the evaluation is a partial rootok slice/status is null, and publish the authenticate aggregate only from the later full evaluation.

Requested delete-credentials assessment: PAM_API_PHASES["delete-credentials"] is intentionally a nonmodule boundary: type auth, api pam_setcred, flags PAM_DELETE_CRED, hook null and dispatch absent; pamApiBoundary returns null moduleHook/rawReturn/actions/accumulators and marks the row inapplicable, matching the interface ledger. In PAM01, actual module cleanup is modeled by phase("setcred","delete"), which dispatches pamEvaluate(...,"setcred"), emits the API call and pam_sm_setcred rows with PAM_DELETE_CRED, and records setcred-delete; the delete-credentials boundary only releases the bookkeeping object afterward. The descriptor therefore does not itself omit actual cleanup. The defect is the existing Unix integration's misuse of the normal setcred descriptor for that event (finding 2).
