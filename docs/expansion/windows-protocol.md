# Windows authentication protocol worksheet

All examples are Microsoft protocol references, not live Windows interoperability evidence. Synthetic credentials and symbolic crypto are teaching fixtures, not captured traffic. No NTLMv1 or LM successful profile is added. The Keycloak bridge remains Kerberos-only.

## Carrier and error decisions

W01-W08 use persistent HTTP/1.1 Negotiate over server-authenticated TLS1.2. Initial GET /reference without Authorization precedes the bare401 WWW-Authenticate: Negotiate scheme challenge; nondelegating WinRM instead starts an authentication POST /wsman, not a Create-shell operation. Bare Negotiate advertises no inner mechanism list. W07/W08 select NTLM from the explicit client endpoint allowlist=[NTLM] stored in the initial local policy artifact, never from an invented server offer or arbitrary Kerberos failure. NTLMv2 itself is preconfigured. Continuation401 responses carry tokens; final HTTP authentication rejection has no continuing token. W08 and the server-policy negative select Incoming NTLM=Deny all accounts / ServerBlock=true, rejecting NEGOTIATE before challenge/pass-through. STATUS_NTLM_BLOCKED maps to STATUS_NOT_SUPPORTED at the NLMP caller, not directly to a universal carrier packet. DC rejection knowledge reaches S on the protected validation result and C on the separately authored carrier response. NTLM transcript MIC, SPNEGO integrity, TLS and CredSSP binding remain distinct; this profile has no separately transmitted SPNEGO mechListMIC and declares NULL channel-binding input, not Extended Protection.

Every authored HTTP request/response has httpCarrier metadata: requestId, request method/target, responseId/status and grouped innerRecords. A response consumes its one outstanding request. W06's final AP-REP is a field of the same HTTP200 response as the resource body (RFC4559 section5: https://www.rfc-editor.org/rfc/rfc4559.html#section-5), not an extra WWW-Authenticate response followed by unsolicited200. ap-reply constructs the token locally; result delivers the token and opaque body together; mutual-verify accepts the reciprocal proof; result-accept decodes/uses the body only afterward. W19 similarly returns the final token in one authentication response with an empty body before the separate protected shell request.

W03/W04 explicitly configure serverDomain=RESOURCE and accountDomain=CORP. MsvAvNbDomainName identifies the server's RESOURCE membership; AUTHENTICATE DomainName and ResponseKeyNT retain the CORP account authority. These are different fields and identities (MS-NLMP2.2.2.1: https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-nlmp/83f5e789-660d-4781-8491-5f8c6641f75e). RESOURCE trusts CORP for user validation: S -> resource DC -> account DC and reverse results use two independently keyed Netlogon channels. No Kerberos referral is involved. W04 rejects the missing direct route at DR without contacting D. Derived negatives inherit the same server/account domain split.

## CredSSP v6 message and object ledger

1. Client policy permits the exact target; explicit credentials remain client-local. A denial can happen before networking.
2. Inner TLS handshake completes. Grouped handshake abstracts record fragmentation, certificate-chain and Finished packets; its successful event implies the separately stated checks, not user authentication.
3. SPNEGO establishes the chosen host mechanism context. Kerberos includes AS/TGS acquisition, KDC authoritative principal-key preauthentication verification and encryption, separate client reply validation, AP-REQ validation and reciprocal AP-REP verification. Host acceptance and client reciprocal acceptance are independently timed. NTLM includes negotiate/challenge, client proof/key/MIC construction, last AUTHENTICATE, separate local SAM or Netlogon validation, authority result/key return, acceptor exported-key recovery, transcript MIC/target/freshness checks and only then context completion.
4. The last client mechanism token and pubKeyAuth are one TSRequest, never two packets. NTLM client can construct the candidate key and binding before server validation; the target verifies only after its mechanism completes. Kerberos's last client AP-REQ likewise shares the message with pubKeyAuth. Receiver possession is not acceptance.
5. Binding input is ASCII("CredSSP Client-To-Server Binding Hash\\0") || nonce32 || ASN.1 encoded SubjectPublicKey. Reverse proof substitutes "CredSSP Server-To-Client Binding Hash\\0". Encoded SubjectPublicKey excludes the SPKI wrapper and full certificate. Magic terminators and 32-byte nonce are mandatory fixture assertions. Early client SHA256 binding is sealed with the then-available initiator key (Kerberos AcceptorSubkey=0); reverse binding and later authInfo use the completed Windows AES acceptor key (AcceptorSubkey=1). NTLM retains ExportedSessionKey. All are carried inside TLS.
6. Target verifies client binding locally, creates reverse proof, delivers it, client verifies locally. In HTTP-CredSSP the locally prepared AP-REP and reverse binding are inner fields of one TSRequest carried by one response to last-token-binding; server-binding delivers both, then mutual-verify and binding-verify-client independently validate them. Raw CredSSP retains its separately authored inner records without pretending they are HTTP responses. Binding rejection stops before authInfo construction/export and preserves prior accepted histories.
7. Client constructs TSCredentials credType 1 with TSPasswordCreds and seals it. Wire authInfo is opaque; receipt creates only a sealed target inbox holding. A separate successful unwrap creates readable delegated credentials at H. H is a legitimate password recipient only at unwrap; other actors never gain that permission.
8. Ordinary CredSSP ends at recovery. Local Windows logon is a distinct operation, not implied by mechanism authentication or export. W13 allows recovery then denies the chosen remote-interactive logon right; disclosure history is retained.

Initial password ownership is client-only. NTLM-only account-record is the authority's NTLM verifier; Kerberos profiles instead provision a distinct D-only kdc-account-key AES256 database handle corresponding to C's independently owned client-account-key material. as-preauth-verify uses D's authoritative key for timestamp verification, and as-reply records its EncASRepPart encryption use; its layer references the D copy, never the C handle. C's later AS reply processing uses the corresponding local material without acquiring the KDC database copy (RFC4120 section3.1.3: https://www.rfc-editor.org/rfc/rfc4120.html#section-3.1.3). Ordinary/Restricted Admin second-hop AS exchanges analogously have H-local downstream-account-key and D-only downstream-kdc-account-key for the actual CORP alice or HOST$ principal. Neither handle travels as a secret wire field. Service keys remain service/DC-only; krbtgt stays KDC-only. KDC-issued session keys are acquired by recipients only after reply validation. NT hash/ResponseKeyNT, client candidate SessionBaseKey, validator SessionBaseKey return, ExportedSessionKey, wrapped exported key and MIC remain distinct. The NTLM MIC and wrapped key are never Netlogon account-verification inputs. Exact transient receipts/releases and opaque/decoded permission boundaries remain authored; no automatic expiration/secret erasure is invented.

## RDP and redirection decisions

MS-RDPBCGR RDP_NEG_REQ 2.2.1.1.1 and RDP_NEG_RSP 2.2.1.2.1, page revision 2026-03-06: https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpbcgr/902b090b-9cb3-4efc-92bf-ee13373371e3 and https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpbcgr/b2975bdc-6d56-49ee-9c57-f2ff3a0b6817 . Request protocols and required-mode bits are independent of selected protocol and support bits. Selected HYBRID_EX includes Early User Authorization Result PDU after CredSSP and before the grouped Basic Settings/Channel Connection/Licensing/Capabilities/Finalization sequence. HYBRID omits that PDU and still requires completion of those connection phases before desktop-ready. These grouped RDP phases are explicitly teaching macros, not invented packets.

Restricted Admin request flag 0x01 requires response support 0x08, sends protected credType 1 with empty domain/user/password strings, and downstream network access uses H's machine identity, not the interactive user's password. Remote Credential Guard request flag 0x02 requires response support 0x10, requires Kerberos on the initial direct RDP connection, and sends protected credType 6 TSRemoteGuardCreds. packageName=Kerberos and credBuffer remain opaque and implementation-specific. No separately decoded ordinary user password or usable copied user TGT is invented at H. MS-RDPEAR revision 10.0 (2024-04-23), section 4.1, explicitly describes KERB_TICKET_LOGON containing a ticket and an encrypted TGT session-key structure within the opaque initial package context; the lesson does not claim that opaque buffers contain no ticket bytes. H constructs the downstream TGS request, redirects protected-key operations to C, contacts the KDC itself and legitimately holds the resulting service ticket. Channel close does not revoke issued service tickets or independently established resource sessions. Required-mode unsupported has separate restricted-admin and remote-credential-guard fixtures and never downgrades.

## WinRM decisions

https://learn.microsoft.com/en-us/windows/win32/winrm/multi-hop-support (document commit 0096be582573c61bde692f97392dec72431c48cf, updated2025-03-11) requires explicit credentials, client/service CredSSP enablement and exact AllowFreshCredentials target policy for CredSSP. Outer HTTP CredSSP headers carry base64 inner TLS records, not passwords. HTTP and HTTPS profiles retain independent inner TLS. Its ClientHello, grouped server handshake, grouped client key-exchange/Finished and final server Finished each have correctly paired carrier requests/responses; multiple TLS records within a flight are not extra HTTP responses. Only the final inner Finished establishes inner TLS. AP-REP/reverse-binding share their HTTP response; authInfo's request receives the separate final HTTP200 authentication completion. The subsequent protected Create-shell request, H unwrap, RootSDDL check, shell creation, returned opaque handle and C verification/acquisition are separate in both CredSSP and nondelegating Kerberos. CredSSP WSMan bodies use inner TLS; nondelegating Kerberos uses its retained Kerberos first-hop context, never fake delegated credentials. A declared grouped command/receive request precedes execution/output. W19 detects unavailable user credentials at H, returns protected command failure, and C learns only after verifying/decoding that return; no HOST$ substitution, R authentication or shell destruction. W23 likewise returns the actual resource denial without erasing prior password/identity history.

## Independent negative expectations

Before each delivery, receiver possession/knowledge is unchanged. Before local proof validation there is no accepted context. Before authInfo unwrap there is no readable delegated credential. Before local logon there is no Windows logon context. Before RDP connection finalization there is no ready desktop. Before downstream authentication there is no downstream identity; before ACL enforcement there is no resource access. Bad NTLM proof, wrong authority, expired prerequisite, route failure, blocked NTLM, binding direction/nonce/key mismatch, absent combined-message field, denied delegation, post-disclosure logon denial, both unsupported required modes and unavailable RCG Kerberos each have an independent stop predicate. Failed downstream access never deletes an established first-hop session. All 23 per-preset expectations are recorded in windows-scenarios.json; model tests must compare canonical prefixes to these independently written predicates.

## Representative provenance and exact wire visibility

KDC-generated TGT and target service session keys exist first at D's issuing reply. C receives only protected material, acquires the decoded key after validating the relevant reply, and never learns krbtgt/service long-term keys. The initiator subsession key is separately client-generated. At AP verification H gains its own ticket/key view. Client-created TSPasswordCreds exists at authInfo construction, while H acquires its decoded copy only at successful unwrap. A later denial cannot erase this receipt. Opaque wire bytes/formulas are inspectable by their legitimate holders without exposing decoded secrets; every protected form has a separate representation and permission set. NTLM proof/blob/challenge instances travel through the authored AUTHENTICATE and Netlogon occurrences, without transmitting the local NT hash/response key. W01 declares no unused CredSSP binding/nonce.
