# Network access protocol worksheets

The companion network-scenarios.json is an independently authored expected-behavior manifest, written before animation code. All values are symbolic teaching fixtures. No live interoperability run has been performed. G01 remains open. The scope is 23 fixed presets, not a production implementation.

## NPS implementation boundary

The Microsoft EAP guidance source was independently retrieved on 2026-10-21: page ms.date 2024-06-27, updated_at 2025-09-15, source commit `16dafaddc757fb0b4ad7e5f8da33fbfc888fbcd4`. Its TLS 1.3 section explicitly says NPS does not support TLS 1.3 and Windows clients do full authentication rather than resumption. Product builds in this lesson are configuration targets, never a fabricated tested patch build.

Windows Server 2022 NPS and Windows 11 24H2 are a documented configuration model; no live interoperability run and no exact tested patch build claimed. [Microsoft EAP guidance](https://learn.microsoft.com/en-us/windows-server/networking/technologies/extensible-authentication-protocol/windows-11-changes#tls-13) says NPS does not support TLS 1.3. Use a full TLS 1.2 handshake: server certificate and CertificateRequest, peer Certificate/ClientKeyExchange/CertificateVerify, ChangeCipherSpec and Finished in each direction. Certificates are visible before TLS 1.2 encryption, unlike the TLS 1.3 encrypted certificate flights. The local certificate-to-account check requires a configured strong binding under [KB5014754](https://support.microsoft.com/en-us/servicing/os/windows-server/2022/05/kb5014754-certificate-based-authentication-changes-on-windows-domain-controllers), for example SID extension matching the account or an explicit strong mapping. UPN alone is not sufficient. [Certificate requirements](https://learn.microsoft.com/en-us/troubleshoot/windows-server/networking/certificate-requirements-eap-tls-peap) and [NPS policy documentation](https://learn.microsoft.com/en-us/windows-server/networking/technologies/nps/nps-top) distinguish validity, mapping and authorization. The scoped account-service check is not a fictional LDAP bind or Kerberos AS exchange.

## Ownership and envelopes

The peer terminates EAP-TLS with the EAP server. EAPOL is peer/NAS only. Backend RADIUS is NAS/server, or separate NAS/proxy and proxy/home associations. A pass-through NAS cannot read TLS traffic secrets, private keys, EMSK or encrypted certificate fields. It may receive authorized MSK halves using the explicitly named MPPE carriers. The proxy can unwrap/reprotect those hop-protected carriers but not TLS ciphertext. AAA forwarding key copies are deleted after forwarding; local lower-layer caching is separately declared. Endpoint private-key handles and trust stores remain local. Trust provisioning is an initial condition, not an online CA flow.

A receipt creates an opaque pending holding at fraction 1. A later local event validates or rejects it. Only a verified correlated response permits enforcement. Protected success and Finished do not themselves open the controlled port. Wi-Fi ends at EAP access decision complete; Wi-Fi link establishment not shown. No MACsec or Internet reachability is implied.

### Corrected exporter, NAS identity and transport boundaries

RFC9190 section 2.3 defines `TLS-Exporter("EXPORTER_EAP_TLS_Key_Material", Type, 128)` with `Type` the single byte `0x0D`, not an empty context or ASCII hex text. MSK is output octets 0-63 and EMSK is output octets 64-127 (zero-based). Both local exporter events expose label, byte-valued context, output length and exact split separately; each endpoint's distinct local MSK/EMSK object records the same provenance. This is not the TLS1.2 RFC5216 PRF used in NPS. No Method-Id or EAP Session-Id exporter is taught here.

Every Access-Request and Accounting-Request includes the stable original NAS-Identifier, `switch.corp.example` for wired examples and `ap.corp.example` for the bounded Wi-Fi AP. This applies to all EAP/NPS continuations and failure acknowledgements, both proxy hops, accounting retries, the independent post-Disconnect Stop and the endpoint-decoded RADIUS/1.1 request, including named inputs. A proxy preserves the NAS identity rather than replacing it with itself. NAS identity does not replace the adjacent source-address/secret association or authenticated TLS transport peer used to select trust. The symbolic packet views omit unrelated optional attributes; no request header view deliberately omits mandatory NAS identity.

For NET-T01, each of the eight `radsec:` backend transmissions is an actual symbolic outer TLS application_data record. Its existing source event and packet artifact IDs remain stable. The `outer-wire` representation contains only `TLS record: SYM(outer RadSec TLS1.3 application_data radsec:<suffix> ciphertext)`. Code, RADIUS identifiers/authenticators, State, EAP-Message, policy and protected MPPE carriers are not substituted into this wire representation.

Each transmission is immediately followed by `<source-event-ID>-decode`, a separate receiver-local operation. It releases only that receiver's `outer-wire` pending inbox and acquires the same `<source-event-ID>-packet:g1` artifact as `radius-decoded` in the decoded packet inbox. Later original local validation consumes that decoded inbox. Exact object history therefore retains both the original ciphertext occurrence and the local decoded occurrence, rather than upgrading a selected wire replay to decoded fields.

NET-05 authors all 53 recovered field occurrences across those eight decode events as actual receiver-local `decrypt` operations, not glossary `inspect` context. Attribute Replay path therefore follows the same local decode event and canonical cursor as whole-journey playback. Each occurrence retains its `radius-decoded` representation, original recovered value, receiver, field path, source event, instance ID and exact-value reference; it never manufactures a clear RADIUS transmission. Genuine inspection-only context stays outside replay. The source, held-object and mounted-app regressions specify these boundaries; their addition is not a claim that the current checks or native browser gates have run.

Outer send layers reference the sender's local key object (`nas-outer-tls:g1` or `server-outer-tls:g1`); local decode layers reference the receiver's independently held key object. Neither key is transferred. Outer decryption reveals RADIUS but does not decrypt inner EAP-TLS certificate flights or protected success, unwrap RFC2548 MSK halves, validate the RADIUS result or admit service. At `radsec:accept` no separate MSK-carrier holding exists yet; `radsec:accept-decode` acquires only its still-protected carrier, `radsec:verify-reply` validates/unwraps it, and `radsec:enforce` alone admits the second session. The completed UDP transaction remains independent throughout.

The independent JSON worksheet now records these requirements in `reviewCorrections`, every request's NAS identity, and each RadSec transmission's distinct `fields` (wire), `decodedFields`, decode event/actor, representation and directional key references. Source categories are authored per RFC, without a catch-all Standards Track default; RFC3579 and RFC2869 are Informational while RFC6614 and RFC9765 remain Experimental.


## Failure and observer knowledge

Malformed integrity and unknown/untrusted dynamic clients are silently discarded, not given a fabricated NAK. Certificate rejection is detected by the endpoint with the failing trust/name/use/time/revocation check and an appropriately protected TLS alert after TLS 1.3 ServerHello. Wrong State in the illustrative TOTP policy terminates context with configured rejection, not a universal RADIUS rule. A lost ACK leaves the controller uncertain even when NAS has already changed or removed the target session. Duplicate authentication requests use a cached response under one transaction; late replies cannot advance another transaction. Accounting repeats update delivery knowledge without duplicating logical records. No unrelated session is removed.

## Independent negative-path contract

The JSON manifest contains 23 fixed worksheets and 68 named inputs that do not add catalog entries. Each negative record has its actual detector actor, detection event, failing wire field or transport condition, local check, propagation, detector-boundary predicates, final predicates, actor-local knowledge and object consequences. These expectations are literal specifications, not values obtained by running the scenario builder or copying the successful terminal predicate. Event/path bindings were refined after initial worksheet authoring; the protocol expectations remain independently specified.

For example, an incorrect recovered password is detected by AAA and produces the selected authenticated Access-Reject. A reply with an invalid Response Authenticator, or a reply bound to another NAS association, is detected by the receiving NAS and discarded: AAA may have accepted locally while NAS has no trusted outcome and cannot admit access. Missing or altered issued TOTP State prevents factor evaluation; invalid versus expired TOTP is a separate validator failure. Source/integrity/freshness failures on dynamic requests are discarded without a fabricated NAK, whereas an otherwise authenticated request naming another NAS produces NAK 403. Unsupported service 405, unsupported attribute 401 and missing session 503 have separate operation checks. Lost dynamic ACK leaves the completed NAS action intact while controller knowledge is unknown.

The first proxy return-state failure happens on the initial Start challenge, before an inner TLS handshake or MSK/EMSK exists. Invalid incoming NAS-proxy integrity is checked before routing and silently discarded. A disallowed configured home candidate is not forwarded; this selected input gives NAS no trusted result and a timeout. That policy is distinct from the separate unknown-realm preset's configured local Access-Reject. Proxy-State preserves ordered upstream context and removes only the forwarding proxy's own value; it is not the EAP server's State.

NET-T01 contains two real, separately scoped histories in the same fixed preset: complete UDP EAP access, then a new mutually authenticated outer RadSec association and complete second inner EAP access. It is not a hidden factory-only transport branch. Outer transport identities/keys and each inner EAP identity/key generation remain distinct. Rejecting the second outer peer cannot erase the first UDP session.

NET-X02 distinguishes a legacy no-ALPN server from disjoint ALPN lists. The former can send ServerHello and encrypted extensions without ALPN; the strict client derives/decrypts, detects absence and closes without application traffic. An ALPN-aware server with no overlap sends no_application_protocol120 and closes before ServerHello in the selected failure. It never selects unoffered radius/1.0. Neither path is Access-Reject, UDP fallback or evidence of NPS RADIUS/1.1 support.

## Inventory and integration contract

The object worksheets use endpoint-specific IDs, exact authored symbolic values, representation readers and local lifetimes. Private keys, TLS state, transcripts and EMSK have no fabricated wire representation. Equal locally derived endpoint keys are separate objects. Public certificates acquire actual receiver holdings at receipt/decryption/validation boundaries: TLS 1.3 encrypted certificate fields are not readable by the pass-through NAS/proxy, while the selected TLS 1.2 public certificate flights are visible before ChangeCipherSpec. RADIUS/1.1 transport certificate decryption at nas-derive precedes the separate trust observation at nas-peer-check.

The implementation exports NETWORKLAB_ATTRIBUTES, NETWORKLAB_SOURCES as an array, NETWORKLAB_SCENARIOS with all 23 fixed IDs, and buildNetworkHeldObjects(args). The QA-only buildNetworkScenarioFixture(id, {variant}) accepts the named negative inputs; it does not add catalog entries or mutate canonical field definitions. Held inventories are authored explicitly in model.networkInventory, not reconstructed from attribute operations or labels. Packet inbox receipt and receiver-local consumption are explicit; a remote endpoint's cleanup cannot clear another actor's holdings.

The two owned test files author independent canonical-state/held-object boundaries, exact protected carriers/readers, named input cases, duplicate-safe logical operations, accounting knowledge, target-only dynamic cleanup and bounded Wi-Fi completion. The negative worksheet test compares the independently specified detector and final predicates with the selected fixture when the parent runs verification. No worker build, test, lint, formatter or smoke command was executed. Main reported that R01/E01 passed its actual UI representative gate before authorizing the remaining presets; full integrated parent verification remains required.

All network SYM/HANDLE values remain symbolic. The separate expansion crypto runner covers selected PAKE/Windows fixtures, not computed RADIUS authenticators, MPPE hiding, TOTP, TLS exporters or the TLS 1.2 PRF. No unrelated vector ID or fabricated computed-byte evidence is attached. No live AAA/NPS interoperability, packet capture, exact tested patch build or protected Wi-Fi data-plane test is claimed. Manual G01 remains open by explicit user choice. Nothing in this deliverable authorizes push, deployment or upload before Astra review.
