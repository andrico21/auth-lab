<h2 id="required-corrections">3. Required corrections</h2>
<h3 id="l10n-r01-protected-names-and-dnssec-verdicts-are-missing-from-localized-explanations">L10N-R01
— Protected names and DNSSEC verdicts are missing from localized
explanations</h3>
<p><strong>Priority: P1.</strong> The catalog’s typed
protected-parameter checks can only protect occurrences actually
classified as protected. Several formal entities, field names, actor
names and DNSSEC result labels are instead classified as ordinary prose
and translated away. This directly contradicts the user’s constraint and
plan sections 2, 4 and 6.</p>
<p><strong>Concrete shipped behavior:</strong></p>
<ol type="1">
<li><code>step:web-bff-redirect</code> / <code>detail</code> says that
the redirect includes the public <code>PKCE</code> challenge,
<code>state</code>, <code>nonce</code> and a registered <code>BFF</code>
callback; the verifier and confidential <code>client_secret</code>
remain on the backend. Russian, Ukrainian, Arabic and Polish replace
both exact parameter names <code>state</code> and <code>nonce</code>
with ordinary translated words; French replaces <code>state</code>. The
same message does protect <code>PKCE</code>, <code>BFF</code> and
<code>client_secret</code>. Schema <strong>4714</strong>, binding
<strong>47683</strong>, demonstrates that protecting <em>some</em> terms
in a sentence does not establish the others are covered.</li>
<li>In <code>field:cibaLoginHint</code> / <code>purpose</code>, the
actual <code>Realm A</code> actor name is translated away in Russian,
Arabic, French and Polish. In Arabic, the generated operation detail for
<code>step:lab-krb-spake-success-advertisement</code> replaces the
canonical actor identifier <code>spake-kdc</code> with a generic
description. These are not merely different translations of surrounding
explanation.</li>
<li><code>field:serviceAccessSignature</code> / <code>purpose</code>
translates the formal role <code>resource server</code> away in all
seven catalogs. <code>lesson:lab-mcp02</code> translates away
<code>authorization server</code> in all seven. An independent
source-table screening with exact per-binding overrides found
<strong>12/12</strong> <code>resource server</code> bindings missing the
exact literal in each locale; <code>authorization server</code> was
absent from <strong>64</strong> bindings in
Russian/Ukrainian/Hebrew/Arabic/French and <strong>60</strong> in
German/Polish. These are screening counts, not a claim that each row was
separately seen on screen. The field and MCP title were also exercised
through the actual resolver/renderer. The Russian BFF step was
separately exercised through the production step renderer.</li>
<li>In the mounted Arabic Compact app, DNSSEC-09’s case
<code>cname-bogus-target</code> displays a localized caption containing
neither the source <code>cname</code> nor <code>bogus</code>. The
<code>cname-insecure-target</code> caption likewise omits
<code>cname</code> and <code>insecure</code>. DNSSEC-11’s completed
<code>tcp failure not cryptographic bogus</code> step displays an Arabic
title containing neither <code>tcp</code> nor <code>bogus</code>. The
machine case IDs still exist; that does not restore the missing
human-visible formal labels.</li>
<li>The Russian and Arabic versions of
<code>Accept non-bogus data or withhold a bogus answer</code> replace
<code>bogus</code> with an explanation about a check not finding
invalidity. That wording risks suggesting that validation was actually
performed and passed. <code>non-bogus</code> must not be silently
narrowed into verified/secure: <code>insecure</code> and
<code>indeterminate</code> are distinct concepts, and the scenario’s own
reliance decision still controls behavior. This review does
<strong>not</strong> assert that an RFC requires accepting every
indeterminate response.</li>
</ol>
<p>The status issue is context-specific: other tested DNSSEC definitions
retain their four labels correctly. Do not report that every DNSSEC
translation is wrong. The independent resolver probe covers 63
context/locale combinations, while the case and step above were
additionally checked in the mounted source app; neither is a
native-browser/AT run.</p>
<p><strong>Likely cause, not a complete audit:</strong>
<code>source/tools/verification/localization/protected.mjs</code> uses
structure/case heuristics that miss simple names such as
<code>state</code> and <code>nonce</code>, as well as multiword roles
and some actual actor labels. The corresponding schema may have no
protected parameters, so a no-missing-placeholder compiler result cannot
catch the omission.</p>
<p><strong>Additional renderer boundary:</strong>
<code>attributeButton()</code> emits sampled <code>client_id</code> as a
<code>code</code> node without an explicit <code>translate="no"</code>
directive or protected ancestor. This was observed in source and emitted
DOM for both presentation paths. The app’s built-in locale did not
change that sampled value, and no external browser translator was run;
the observed defect is the missing HTML protection directive, not
demonstrated corruption by an external translator.</p>
<p><strong>Worker correction:</strong></p>
<ul>
<li>Re-inventory <em>semantic occurrences</em> against authoritative
attribute/claim/parameter names, formal protocol roles, result labels,
RFC entities, authored actors and machine-visible case labels. Add
context-aware protected references, including simple lowercase
identifiers and multiword names. Do not blindly treat every ordinary use
of the English word “state” as an OAuth parameter or replace every
adjective “insecure.”</li>
<li>Correct affected source contracts, source fingerprints, per-binding
overrides, catalogs and generated resources for <strong>all seven
locales</strong>. Keep exact source spelling/case such as
<code>cname</code> when it is the protected source entity; allow the
human-language explanation around it to be natural.</li>
<li>Repair the meaning of the affected DNSSEC explanations and
independently sample the same risk across OAuth/OIDC, Kerberos, Windows,
PAM, SMB/NFS, Kubernetes and MCP. Maintain each exact source prefix,
actor, trust direction and uncertainty. No broad automated rewrite may
invent validation, permission or acceptance.</li>
<li>Add direct rendered and exact emitted-bundle tests for the examples
above, plus automated registry checks whose input is independent of the
current heuristically generated protected registry. Include actual UI
controls, <code>translate="no"</code> / directional isolation for
protected names where planned, raw clipboard bytes, and
English/canonical-state invariants. Add regression tests for
