# DNSSEC D0 publication source dispositions

Research cutoff: 2026-10-23. Scope: source groups S13-S21, S25, S27 and S29; independent expected cases DNS02 and DNS12-DNS19. No production evaluator was imported or implemented. No build, regression suite, lint or formatter was run by this slice.

## Captured identities and failures

`source-ledger-publication.json` contains per-request UTC retrieval start, requested/final URL, HTTP status, response headers, byte length, SHA256 and immutable response-body path. The 29 required primary URLs all returned HTTP 200. These are 26 RFC documents, two IANA registries and the RFC Editor DNSSEC discovery index. The index is a discovery aid, not standards authority. Reading-copy `.txt` files are derived from raw HTML and never replace the immutable `.raw` bodies.

An additional erratum retrieval produced an actual failure: `https://www.rfc-editor.org/eid4935/` returned HTTP 404, 15 bytes, SHA256 `53c6279bf75b5b7abf1fa6349de51bf3284ee5de7cf0c720cd131303b6a6859e`. It is retained as `sources/publication/rfc8080-erratum4935-first-attempt.raw`. The alternative `https://www.rfc-editor.org/errata/eid4935` redirected to `https://errata.rfc-editor.org/eid4935/` and returned HTTP 200, 14685 bytes, SHA256 `85f3ea08fbb886617726e96ad3beeebb513118b057a3cd5ffa39b9fb9dd6807b`. Erratum 4935 is Technical, Verified, reported and verified 2017-02-16; it corrects RFC8080 section 6. Missing RRSIG algorithm identifiers, labels 3 instead of 2, and resulting invalid signature bytes are all corrected. Original RFC bytes and failed retrieval remain unchanged. The numeric slice owns the independent corrected-example verification and preserved original parse failure; this slice does not claim to have rerun it.

RFC8078 section 4 also has VERIFIED TECHNICAL erratum 5049, reported 2017-06-23 and verified 2017-08-10. The captured `https://www.rfc-editor.org/errata/rfc8078` response redirects to `https://errata.rfc-editor.org/search/?rfc_number=8078&presentation=records`: HTTP 200, 15097 bytes, SHA256 `d55e5e1274bf2ff242da65559ef25bb1afea5a6e6e7756a347c273db1d4b2b01`. It corrects the delete presentation to `CDS 0 0 0 00` and `CDNSKEY 0 3 0 AA==`, both with exactly one zero payload octet. The plan and original RFC's trailing-single-`0` notation must not be treated as a valid one-character Base64 encoding. Actual RDATA hex is `0000000000` for CDS and `0000030000` for CDNSKEY. Sentinels are signed by the existing authorized child key; the sentinel is not a usable DNSSEC key or digest.

Thus 32 requests are preserved: 31 successful responses and one 404. There are no unresolved required-source retrieval failures. This is not a claim that every possible erratum for all 26 RFCs was independently audited. The required RFC4034/RFC4035 errata work belongs to the resolution shard.

## Operational source decisions

- S13: RFC6781 and RFC7583 are Informational, not universal fixed-timer mandates. Default DNSKEY TTL 3600, maximum signed-data TTL 7200, parent DS TTL 86400, child propagation 300 and parent propagation 600 are explicit synthetic choices. Every rollover retains actual cached generation dependencies. RFC7583 Double-KSK publishes both KSKs and both DNSKEY signatures, waits `DprpC+TTLkey`, then submits a replacement DS. Actual parent visibility, not acknowledgment, marks activation/retirement. The old KSK and signature survive `DprpP+TTLds` after replacement. Double-DS instead overlaps parent DS first; Double-RRset is not the named Double-KSK case. CSK transitions independently track ordinary RRset and DNSKEY authentication constraints; RFC7583 explicitly excludes CSK and algorithm/TTL changes from its formal scope.
- S14: RFC5011 states Start, AddPend, Valid, Missing, Revoked and Removed remain explicit. Add eligibility is the later of 30 days and first-observed original DNSKEY TTL expiry, followed by a fresh validated B-containing observation. A mere timer expiry does not install a key. Authenticated absence resets AddPend; unreachability alone does not. A Valid key that disappears becomes Missing and remains trusted until explicit revocation. Revocation needs the key's own valid signature with REVOKE set and is immediately permanent; the 30-day removal interval is database bookkeeping, not continued trust. Flags 257 to 385 changes tag 22775 to 22903 while retaining the same public-key lineage. Initial and manual recovery trust is out-of-band. RFC9718 replaces RFC7958 as current root-anchor publication context.
- S15: RFC8901 Model 1 leaves KSK private custody solely with the zone owner and distributes a common signed public DNSKEY set; each provider keeps its own ZSK private. Model 2 has separate provider KSK/ZSK sets, all public ZSKs in each provider's DNSKEY set, and parent DS for both KSKs. A provider switch with a cached foreign keyset only works if the signing key is present. The missing-key failure case explicitly exhausts compatible alternatives; it does not claim recovery via another authority is impossible in all deployments.
- S17: DS2 hashes canonical owner wire bytes concatenated with DNSKEY RDATA, not TTL or a whole RR header. Algorithm 13 uses 64-byte public x||y and 64-byte signature r||s. Algorithm 15 uses 32-byte public and 64-byte signature values. Domain-name canonicalization is field-specific; opaque TXT case changes are signature-input mutations. A key tag is not unique key identity.
- S19: CDS/CDNSKEY are child intent, not parent publication. Ordinary signals must authenticate through an already authorized key and preserve a usable resulting path. Absence/NODATA means no change. Removal requires exact authenticated singleton `CDS 0 0 0 00` or `CDNSKEY 0 3 0 AA==`, applying verified RFC8078 erratum 5049 to the original trailing-single-`0` notation; malformed fields or additional records are not a valid delete signal. Signing continues until prior DS cache dependencies have cleared.
- S20: RFC9615 initial bootstrap requires parent DS absent, at least one out-of-domain delegated NS, direct uncached apex claims, and an independently secure operator signaling namespace under every eligible NS name. In-domain child self-signatures cannot create missing independent trust. RFC10026 requires intent consistency and validation continuity before DS updates. Selected new DS TTL 600 seconds is within its 5-15 minute recommendation but cannot shorten old remote 86400-second cache entries. Manual recovery must remain possible. Registrar update locks alone do not stop automation; a registry update lock blocks registrar EPP updates but not the registry's own automation. In-band DELETE does not suspend automation. Out-of-band full DS removal does suspend the selected automation until nonempty DS provisioning; an ordinary nonempty manual change does not categorically suspend it. Do not infer resumption from SOA serial changes. Requests execute at the next publication opportunity after verification. Reporting distinguishes operator/technical contacts, registrar change notification, prolonged registrant escalation and local deduplication policy.
- S21: RFC9975 requires all addresses of all parent-delegated NS hostnames, including available glue and validating address discovery. Consistency applies to received responses; NODATA counts, timeout does not. Retry before declaring permanent unreachability. Every inconsistent state aborts all requested creation/alteration/removal. Compare eligible referenced keysets, not byte-identical RRsets of every digest type. Current eligible CDS consistency digests are only type 2 because the captured Implement-for-Delegation column says MUST only there. Parent publication digest choice is separate. RFC7477 CSYNC synchronizes NS/glue, not DS.
- S25: RFC8945 is the current TSIG reference, not obsolete RFC2845/4635. HMAC authenticity/integrity and authorization are separate. Valid but unauthorized UPDATE yields authenticated REFUSED; known-key MAC mismatch yields NOTAUTH and TSIG BADSIG 16, with unsigned error response. A signed zone is not authority to UPDATE or AXFR. An offline signer can transfer a public signed zone to a secondary with no signing private key. NOTIFY triggers checking, not transfer; IXFR/AXFR candidate installation waits for complete checked transfer. ZONEMD expected apex SOA/digest must be authenticated, serial/scheme/hash/length checked, then whole-zone checksum compared. Available RRsets can validate while whole-zone integrity fails. The original lifecycle supplement supplied checksum-only evidence; the later `numeric/zonemd-auth-fixtures.json` now supplies separately signed SOA/ZONEMD, a regenerated NSEC bitmap including ZONEMD before digest calculation, and an explicit synthetic root-to-child authentication path. The selected case changes unsigned delegation glue from 192.0.2.200 to 192.0.2.201 at serial 2026102301, retaining valid signed RRsets while breaking the authenticated whole-zone digest. This supersedes the earlier checksum-origin limitation for this fixture only. No live origin, interoperability, TSIG, ZONEMD or DNSSEC confidentiality claim is made.
- S27: RFC8749 moves DLV RFC4431/5074 to Historic. Do not implement or teach DLV as a current trust path. The RFC Editor index confirmed newer document identities, not their normative meaning.
- S29: RFC9859 DSYNC discovers the notification endpoint. NOTIFY(CDS) covers both CDS and CDNSKEY changes. Null/unsupported schemes and port zero are unusable; targets need address records. Acknowledgment is not DS acceptance or publication. Retrieve and validate through the ordinary bootstrap/update workflow, including all-address consistency. Notify after public signal convergence. Asynchronous error report channels must be subordinate/equal to a delegated NS name.

## Independent worksheet and numerical boundaries

`worksheet-publication.json` contains 9 lessons and exactly 66 named cases: DNS02 7, DNS12 6, DNS13 6, DNS14 8, DNS15 7, DNS16 10, DNS17 8, DNS18 7 and DNS19 7. Each has explicit setup, custody, sequence, checkpoints, selected outcome, time dependencies, inspection requirements, policy notes and primary section references. First named case is already the default; no extra default row exists. Parent administrative acceptance is `publication.parentAccepted`, actual parent publication is `publication.parentPublished`, and resolver cached generation is only under `cacheEntries`. No leaf query means no fabricated stub/application success. A secure management-object signature does not imply accepted update or whole-zone integrity.

The true protocol baseline is 1792713600, 2026-10-23T00:00:00Z. Numeric bindings name the independent fixture key IDs and actual collision candidates (both tag 46075; first fails, second succeeds), revoked lineage, canonical vectors and lifecycle signatures. The base one-hour RRSIG is not reused at later lifecycle times. The long-window supplement supplies 35-day Original TTL authenticated anchor observations and explicit 120-day teaching signatures, rollover A TTL 7200/DS TTL 86400, day-3 revoked self-signature and day-90 current trust-point DNSKEY. The interrupted-add setup uses original TTL 3600 and a distinct authenticated key-omission observation; it resets day 10, restarts day 20 and can install only after a validated day-50-plus-one-second observation. Long validity windows are selected deterministic fixtures, not operational recommendations.

The final `numeric/record-profile-fixtures.json` contains separately signed CDS/CDNSKEY intent and corrected one-octet delete sentinel RRsets, plus parent-signed DSYNC and separate child-signed CSYNC. Their owner/type/signatures are explicit and are not manufactured by relabeling a DS signature. `numeric/refresh-fixtures.json` supplies the precise same-key expiry-10000 and refreshed signatures for DNS12; actual RRSIG object metadata supersedes removed generic symbolic signature dates. Where a root/parent private key is listed, the synthetic actor is explicitly a co-located signer plus authority, not an implication that every serving authority possesses a private key.

`numeric/long-profile-fixtures.json` supplies actual long-lived root DNSKEY, root-to-example DS, example DNSKEY, child-path, CSK/Ed25519/provider-B answer, dual-algorithm DNSKEY/DS and provider-overlap DS signatures for the selected 95100-second and 175200-second timelines. The worksheet's `selectedSignatureBindingsByCase` names the exact fixture IDs and separates byte-backed reference objects from independently authored symbolic variants. A signature is never attached to a changed owner, type or RRset merely because its key is the same. All packet bit fields use integer 0/1; decision fields remain Booleans.

All seven DNS15 cases are explicitly trust-anchor-management-only. They retain raw DNSKEY receipt, actual authenticated observations, hold-down/reset/revocation/installation state and negative first detectors, but perform no leaf query. Their outcomes therefore have `rcode: null`, no stub response, no leaf use/cache and a pending application result. A successful day-35 or day-90 anchor operation is not presented as validation of an unperformed A lookup.

`numeric/complete-path-fixtures.json` provides an explicit consumed path catalog, not merely independent leaf signatures: every referenced path lists the root DNSKEY, root DS, example DNSKEY, child DS, matching child DNSKEY and answer objects and their actual Original TTL/validity metadata. The CSK final at offset 95100, algorithm final at offset 95100 and provider-B migration final at offset 175200 bind these full long-window paths. DNS15 intentionally consumes no leaf path at all.

The final role-specific supplements close exact membership as well as clock validity: `role-rollover-fixtures.json` signs ZSK-only final `[KSKg1,ZSKg2]` and KSK-only final `[KSKg2,ZSKg1]`, rather than substituting a both-roles-g2 set. `overlap-keysets-fixtures.json` separately signs the three-key ZSK/KSK overlaps, two-CSK overlap and exact Model-1 provider overlap/final sets. Worksheet `roleExactNumericBindings` supersedes generic four-key rollover examples for these cases and retains the selected old-DS Original TTL 86400 when that cache dependency is exercised.

No runtime/live-service/native-validator/manual acceptance is claimed. Parent integration and freeze checks remain separate from this research output. Earlier closure records, G01, predecessor performance conditions and all previous optional rows are intentionally untouched.
