Why DNS-R10 can close

The previous defect was in DNS09 / cname-bogus-target: its separately secure CNAME cache inherited a five-second countdown and null validation time from the failed aggregate lookup. The target’s failure cache was correct; the independent alias metadata was not.

The fix derives alias receipt time from its original occurrence, validation time from the already-existing successful alias-check evidence, and lifetime/proof bounds from the alias’s own authenticated window. It creates no new signature check, packet, receipt or trust event.

At accepted-use-and-cache-boundary, source index 29, protocol time T = 1792713600, independently observed values are:

Property Authenticated alias Failed target
Kind / security answer / secure failure / bogus
Receipt time T T
Validation time T, matching the existing valid alias evidence null
Expiry T + 300 T + 5
Stored remaining TTL at T 300 5
Signature deadline T + 3600 null
Authenticated proof deadline T + 3600, from the alias’s own signature null
Overall lookup SERVFAIL; the target address is refused Same unchanged error outcome

The actual alias cache remains eligible at T+6 and immediately before its original expiry, and is rejected at T+300. Eligibility checks do not renew its receipt or validation time, change the original deadline or mutate the creation-time record. The stored remainingTtl: 300 describes its represented creation clock T; it is not a claim that the remaining lifetime stays 300 at later clocks.

The exact held-object inspector exposes the same corrected record as canonical state. Before cache creation there is neither a current alias cache nor its holding; rewind restores that absence. Full, ordinary-field and exact-object replay agree at equal canonical source prefixes. The target continues to fail independently, and the application continues to receive an error.

The independent semantic probe passed 216 assertions across all seven DNS09 cases, including four alias/target cases. It recomputes the expected expiry from the actual tuple bounds without using the production cache-window helper, links validation time to the pre-existing successful evidence, and confirms that only the affected alias’s three values change. All wire packets, signed/public records and check evidence remain equal to the preceding packet.

Independent source and supplied-standalone inspector probes each passed 404 assertions across 84 positions, with equal results. They cover every full-journey step forward/backward, ordinary-field and exact-object views, actual seeks across cache creation, and reset. The retained native evidence audit passed 294 checks, and both current screenshots visibly show the corrected cache record. After reset, the inspector is hidden and its selection cleared; retained text in hidden markup is not presented as current possession.

These checks close the reported finite model/inspection inconsistency. They do not constitute a general DNS implementation certification, live resolver test or blanket RFC-conformance claim.
