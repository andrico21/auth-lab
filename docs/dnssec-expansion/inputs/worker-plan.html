2. What the learner must understand

The learner should be able to answer: Who supplied these bytes? Who signed this RRset? Why does this validator trust that key? What did the parent assert? Which resolver validated? What does the stub know? Why was the answer accepted, considered insecure, rejected or not determined? Which cached evidence or timer affects the next request?

The interface must distinguish DNS data authenticity from transport protection, DNS transaction authentication, application authentication and authorization. DNSSEC authenticates data and denial evidence; it does not encrypt ordinary DNS, authenticate a human user, authorize file access or independently authenticate a subsequent HTTPS server. A successful signed lookup can be a prerequisite to another lesson without silently granting its permissions. [S01, S02, S23, S24]

3. Standards baseline and modern defaults

Research cutoff: 23 October 2026. Use RFC 4033/4034/4035 with their applicable updates, RFC 6840 clarifications, RFC 9499 terminology and RFC 9364’s DNSSEC standards overview. Old publication dates do not make the foundational DNS wire format obsolete. Conversely, a newer update must not be omitted because a familiar tutorial predates it. [S01, S02, S03, S04]

Decision Worker requirement
Algorithm guidance RFC 9904 supersedes RFC 8624 as the policy reference and points to the IANA registries. Freeze a dated snapshot of the separate signing, validation and implementation columns. Do not collapse them into one “supported” Boolean. [S16]
Default example Use ECDSAP256SHA256, algorithm 13, with SHA-256 DS digest type 2. This is a selected modern teaching profile, not the only conforming configuration. Include Ed25519 or another currently permitted algorithm as an explicit alternative. [S16, S17]
SHA-1 nuance Keep three independent concepts: DNSKEY/RRSIG signing algorithm, DS digest type, and NSEC3 name-hash algorithm. RFC 9905 §2 requires operator treatment of signing algorithms 5/7 as unsupported even while implementation validation support is retained. Do not infer operator acceptance from the registry’s retained validation capability columns. Digest type 1 has its own delegation/validation policy; NSEC3 hashing is a third use. [S18]
Other deprecated algorithms Reflect RFC 9906 and current registries; do not make ECC-GOST or RSA/MD5/DSA a normal signing option. Compatibility/error fixtures must say why they exist. [S16, S18]
Denial default Teach conventional NSEC first. Add NSEC3 with current guidance: zero additional iterations and empty salt; explain when Opt-Out is applicable. Do not present hashed names as encryption. [S07, S08]
Newer denial format Include RFC 9824 compact denial as an explicit profile with capability-sensitive behavior, not a universal property of deployed resolvers. [S11]
Delegation automation Apply RFC 7344/8078/9615 together with RFC 9975 consistency and RFC 10026 operational guidance. An old single-server CDS polling example is insufficient. [S19, S20, S21]
Trust anchor Use a deterministic synthetic hierarchy and an explicitly provisioned anchor. Keep root hints separate. Never learn trust solely from the self-signature of a fetched key. Do not hardcode an old real root KSK as “current.” [S01, S14]

Use synthetic . → example. → lab.example. and names such as www.lab.example. inside an explicitly simulated DNS universe. It must not query public DNS or imply that these fixtures are the real root zone. Fixture time is adjustable and independent of the browser’s wall clock. Document sample TTLs, policy choices and signature lifetimes as fixture values.

At the source-lock phase, capture applicable RFC sections, update relationships and errata statuses. Reference the RFC plus individual verified errata, rather than treating an informative inline-errata rendering as a replacement standard. Reported/held errata are not automatically normative. Verified errata surfaced for RFC 4034: 193, 1062, 3045, 4552; for RFC 4035: 3044, 5226. Check their applicability to the selected fields and algorithms before deriving assertions. [S28]

4. Actors, records and state contract

Actors and ownership

Entity What must be represented
Application and stub Application request/result is separate from DNS messages. Support a conventional stub, a security-aware nonvalidating stub trusting a configured resolver, and a locally validating stub.
Recursive resolver and validator Resolution, validation, trust store and caches are distinct responsibilities. They may share a process; do not invent a network hop between local components.
Forwarder / upstream recursive service Show the actual forwarding chain, validation owner, configured trust and per-hop flags. Forwarder does not automatically mean validator.
Root, parent and child authorities Label zone ownership and delegation cuts. A server can serve several zones without merging their signing authority. Distinguish authoritative answers from recursive service.
Zone operator, signer and private-key store Signing private keys remain at the declared signer/HSM boundary. Offline signing and online signing are different deployment profiles.
Primary and secondary authorities Published zone versions, replication and serving are separate from signing. A secondary need not possess private signing keys.
Child DNS operator and parental agent Child publishes requested DS intent; parent-side acceptance and publication are separate steps. Distinguish registrant, registrar, registry and DNS provider where relevant. Do not invent an EPP/registrar API wire protocol.
Additional signer/provider Use only for DNS18; label each provider’s public key set, private custody and publication generation.
Adversarial or faulty intermediary Bounded tampering/stripping/staleness fixtures illustrate exactly what is detected and by whom. Do not make DNSSEC guarantee availability.

Terminology and role boundaries follow RFC 9499 §§6, 9–11. Use grouped actors and chapters to keep an ordinary lookup readable; not every role needs to be visible at once. [S04]

Field layouts: [S05–S08, S19, S22, S25, S29]. Do not duplicate every field as a permanently visible row in Journey mode; Fields mode must expose the real structure.

State dimensions and provenance

Keep separate received, signatureChecked, chainEstablished, denialChecked, acceptedForUse, cached, returnedToStub and applicationResult transitions. A public RRset is readable before it is trusted. DNSSEC has no “decrypt RRSIG” step.

Use securityStatus together with reason, anchorRef, validationOwner, evidenceRefs, algorithmPolicy, checkedAt and failureStage. Secure, insecure, bogus and indeterminate are not a complete substitute for these facts. RFC 9499 §11 preserves differences in earlier definitions; state the selected interpretation. Distinguish “not yet checked” and “transport failure” from a completed DNSSEC verdict. [S04]

Every message occurrence has its own identity/correlation. A canonical RRset may be carried in several messages and caches. Keep issuer/signing origin, transmitter and current holder separate. Deriving a DS does not make the child the publisher of the parent’s DS RRset. Forwarding does not make the forwarder the signer. Publication retirement does not erase remote cache copies. Never mutate a previously signed representation simply to show a decreasing cache TTL.

Private signing keys must not appear in resolver, stub, parent-agent or network holdings unless that actor independently is the explicitly configured signer. Public-key transfer and local trust acceptance require different events. Model use/verification observations for existing keys rather than reacquiring or recreating them at every check.

DNS01 — Follow a signed lookup

Question: How does a cold resolver obtain and trust an answer?

Trace: application/stub requests A; resolver selects its configured anchor; follows root/parent/child referrals and obtains the needed DNSKEY/DS/RRSIG evidence; authenticates the links and answer; caches accepted data; returns a response; stub/application consumes it at its own boundary. Fetch order is one valid deterministic teaching order, not a requirement that all implementations query identically. Ordinary recursive lookup happens at the resolver; the stub is not shown iterating through all authorities.

Cases: cold-secure, warm-answer-cache, partial-chain-cache, tampered-answer.

Acceptance: the exact answer is present before local checking but not marked trusted; referral addresses are not made secure merely by sharing a message with DS. The warm variant shows which requests disappear and which evidence supports reuse. The tampered RRset is withheld for the checking client. Link to DNS02 for how the signed records were produced. [S01, S02, S03, S04, S05, S06]

DNS02 — From zone data to signatures

Question: What exactly is signed, by which key, and what gets published?

Trace: prepare zone RRsets; create public/private key pairs; canonicalize signing inputs; sign and publish DNSKEY/RRSIG and denial records; derive candidate DS; hand candidate to the separate parent publication process. Teach split KSK/ZSK and combined signing key profiles. KSK/ZSK roles are operational conventions; SEP is not a universal validator key-usage restriction.

Cases: split-ksk-zsk, combined-key, equivalent-presentation, changed-rdata, opaque-rdata-case-change, changed-owner, keytag-collision.

Acceptance: show canonical bytes and signature input boundaries. RR ordering, case of domain-name fields subject to canonicalization, and permitted name compression must not cause invented signature failures. Opaque RDATA such as TXT string case remains signed data: changing it, or changing the owner to a different name, fails verification with the unchanged signature. Colliding tags still select/check actual candidate keys. The root does not sign every leaf RRset. DNSKEY is public; private keys are not DNS records. [S01, S03, S05, S13, S17]

DNS03 — Cross a delegation boundary

Question: Why is one child secure, another insecure, and another broken?

Cases: signed-child, proved-no-ds, supported-ds-mismatch, missing-ds-proof, no-covering-anchor, signed-island-with-local-anchor, unsupported-only-ds.

Acceptance: animate parent-authenticated DS, matching child key and child DNSKEY RRset acceptance. Proved absence of DS can establish an insecure delegation; a missing packet field cannot. A supported DS path that fails differs from an authenticated unsupported-only path. A signed island becomes locally secure only with a suitable independent anchor/path. Expose how local strict application policy can refuse an insecure answer without relabeling it cryptographically bogus. [S01, S03, S04, S06]

DNS04 — Explain a validation decision

Question: Which check failed, and what does the client receive?

Cases: valid, signature-expired, signature-not-yet-valid, wrong-clock, missing-dnskey, missing-rrsig, wrong-signer-or-key, wrong-covered-data, one-valid-plus-one-invalid-signature, dnskey-protocol-not-three, zone-key-flag-clear.

Acceptance: bind each check to the exact key/RRset/signature, time and policy, including DNSKEY Protocol=3 and the Zone Key flag; SEP is not an ordinary validation gate. Support a valid usable signature/path despite an additional unusable signature; do not require every attached signature to pass. Wrong-clock is an explicit resolver input. Show the internal verdict separately from external SERVFAIL/EDE behavior; no positive application answer is accepted in a checking bogus case. Numeric validity-time handling must follow the RFC’s serial arithmetic. [S03, S05, S06, S12]

DNS05 — Stub validation and the AD flag

Question: Does my workstation verify DNSSEC itself or trust a resolver?

Cases: unaware-stub, trusted-resolver-ad, ad-interest-without-do, validating-stub, forged-ad-untrusted-hop, do-zero-explicit-dnskey-query, response-flags-and-cached-ad.

Acceptance: distinguish DO requesting DNSSEC records, query AD signaling understanding/interest, response AD conveying the responder’s assertion, and CD requesting checking-disabled treatment. AA/RD/RA/NOERROR are not security verdicts. DO=0 does not mean “validation off”; explicit DNSSEC-type queries still return their requested type. A locally validating stub owns its anchor and checks evidence. A nonvalidating stub’s reliance requires declared resolver/channel trust; a forged AD bit on an untrusted hop is insufficient. [S01, S03, S23]

In the response-flags case, check recursive CD echoing, DO copying by the responder and receiver-side ignoring of response DO. Do not assert that CD=1 always forces AD=0: already authenticated cached data can meet the applicable AD conditions. [S03, S06]

DNS06 — Who validates when DNS is forwarded?

Question: Where does validation happen in client → local resolver → upstream resolver → authorities?

Cases: local-validates-upstream-fetches, upstream-validates-local-relies, both-validate, upstream-servfail-cd-zero, local-checks-cd-one-data, dnssec-stripping-forwarder, forwarder-loop-or-unreachable, cached-upstream-servfail-cd-zero-then-cd-one.

Acceptance: show queries, flags and results for each hop. A validating resolver can request unchecked upstream data and make its own decision even when its downstream client requests checking. Do not propagate upstream AD as local independent verification. A trusted-upstream profile must declare that trust. Stripped records or transport failure must not silently downgrade a known secure delegation to an unsigned success. Forwarding configuration selects a route; it does not install an anchor. [S03, S23]

The cached-upstream-SERVFAIL case must issue a fresh CD=1 upstream query in the circumstances specified by RFC 6840 §5.9. Keep this cache context distinct from suppressing repeated locally established failures under RFC 9520. [S03, S12]

DNS07 — Prove that a name or type does not exist with NSEC

Cases: nxdomain, existing-name-nodata, empty-nonterminal, wildcard-excluded, no-ds-at-delegation, incomplete-proof, proof-from-wrong-zone.

Acceptance: display name intervals and type bitmaps, then explicitly derive the assertion they support. NXDOMAIN, NODATA and empty non-terminal are different. Where wildcard exclusion or additional evidence is required, a single convenient-looking record is not enough. A denial from one zone cannot be applied across an unrelated delegation. Keep authenticated negative answers separate from transient failure caching. [S05, S06, S09]

DNS08 — NSEC3 and Opt-Out

Cases: nsec3-nxdomain, nsec3-nodata, unsigned-optout-delegation, missing-closest-encloser, hash-parameter-mismatch, excessive-iterations-policy.

Acceptance: explain matching versus covering hashes, closest encloser and next closer; show the actual salt/iteration/hash inputs. The zero-iteration setting still performs the initial hash. Opt-Out does not prove all names in a covered interval absent or secure. Show the limits of enumeration resistance and the authority-side NSEC3PARAM role. Declare expensive-proof handling as a selected policy within current guidance; do not turn a resource limit into a successful proof. [S07, S08]

DNS09 — Wildcards and aliases across zones

Cases: wildcard-positive, wildcard-nodata, wildcard-missing-proof, cname-secure-target, cname-insecure-target, cname-bogus-target, dname-synthesized-cname.

Acceptance: for conventional wildcard signing, relate RRSIG Labels to the reconstructed owner and the required closest-match evidence. Validate each relevant link/target under its own authority; a signed CNAME does not bless the destination address. A CNAME alias’s original name is not the target’s zone. For DNAME, authenticate the DNAME and check the synthesis; do not require an independently signed synthesized CNAME. Keep the RFC 9824 online-signing case distinct. [S05, S06, S11, S26]

DNS10 — Reuse validated cache data

Cases: positive-cache-hit, expired-ttl, signature-expires-first, short-rrsig-ttl, short-original-ttl, negative-cache-hit, aggressive-nsec, aggressive-nsec3, wildcard-synthesis, out-of-proof-range.

Acceptance: distinguish exact cache hits from newly synthesized answers based on validated denial evidence. Show the relevant cache key, proof zone/range, evidence lifetime and signature limit. Apply RFC 9077’s updated NSEC/NSEC3 TTL rules, including valid aggressive use that does not depend on an attached SOA for every cached proof. A new publication does not immediately invalidate an old valid cache. Forbid synthesis outside proof coverage, across an incompatible zone cut, using Opt-Out evidence where disallowed, or after validity ends. [S09, S10]

Compute the effective authenticated TTL bound from received RRset TTL, received RRSIG TTL, RRSIG Original TTL and remaining signature validity. Explicitly exercise each limiting term rather than testing signature expiration alone. [S06 §5.3.3]

DNS11 — Large answers, EDNS and encrypted transport

Cases: udp-complete, udp-truncated-tcp-retry, tcp-blocked, edns-stripped, dot-authenticated-resolver, encrypted-but-bogus-dns-data.

Acceptance: show advertised UDP size, TC and a correlated TCP retry; do not treat a partial response as a complete proof. TCP is a normal DNS transport, not an obsolete workaround. The selected authenticated DoT profile protects the hop and authenticates its configured endpoint; encryption alone or opportunistic use must not imply that identity guarantee. It does not produce an RRSIG or fix a broken DNSSEC chain. Keep transport authentication and DNSSEC result independent. Detailed TLS handshakes can link to existing lessons rather than be duplicated. [S22, S23, S24]

DNS12 — Refresh signatures and roll a ZSK

Cases: resign-before-expiry, zsk-prepublish, zsk-double-sign, old-key-removed-too-early, secondary-lags, signature-refresh-outage.

Acceptance: show publication, activation, overlap and retirement as separate clock events. The resolver continues with the key/signature generation it actually cached. Compare safe rollout with a client whose remaining cached objects no longer compose into a valid path. Refreshing RRSIGs is not necessarily changing the DNSKEY. No arbitrary “wait one TTL” shortcut may substitute for the selected publication, cache and signature timing dependencies. [S13]

DNS13 — Roll a KSK or combined signing key

Cases: ksk-double-ds, ksk-double-ksk-method, combined-key-rollover, parent-ds-delayed, old-ds-cache, premature-old-key-removal.

Acceptance: child DNSKEY changes and parent DS changes have different publishers, schedules and caches. Demonstrate a continuous path for old and new resolver states. A CSK transition must account for both DNSKEY authentication and ordinary RRset signatures. Reducing a TTL now does not shorten a previously cached TTL. Parent acknowledgments and publication visibility are separate. [S13, S19]

Bind the second case to RFC 7583’s Double-KSK timeline; do not confuse it with the Double-RRset method or ZSK double-signature rollover.

DNS14 — Change algorithms and digest policy

Cases: modern-baseline, dual-algorithm-rollover, algorithm-unsupported, unsupported-digest-only, modern-and-obsolete-paths, sha1-signing-disabled, sha1-digest-compatibility, nsec3-sha1-not-signature-policy.

Acceptance: keep publisher generation rules, implementation capability and operator acceptance policy separately inspectable. Use current RFC/IANA requirements for algorithm transitions and usable paths, not an indiscriminate all-signatures rule. Preserve the RFC 9905 distinction explained in section 3. A valid alternative current path prevents an obsolete extra path from automatically poisoning the answer. Document exactly which cases exercise compatibility versus current default operation. [S03, S13, S16–S18]

DNS15 — Install and maintain a trust anchor

Cases: provisioned-anchor, untrusted-self-signed-key, rfc5011-add, add-hold-down-interrupted, revoke-and-remove, offline-misses-rollover, manual-recovery.

Acceptance: teach initial out-of-band trust separately from authenticated RFC 5011 maintenance. Show the specified states, observation history, hold-down timers and revoke processing rather than reducing the protocol to “see a new key, trust it.” Represent the add hold-down as at least 30 days and no earlier than the first-observed RRset’s original TTL expiry, with the required repeated validated observation; removal bookkeeping is distinct from revocation. Use an accelerated display clock with true represented durations. Lost trust does not repair itself from an arbitrary fetched key. Manual recovery is explicit operator action. Trust-anchor replacement differs from parent/child DS rollover. [S14]

Revocation changes DNSKEY RDATA and therefore the derived key tag. Preserve public-key lineage across that change; withdrawal alone is not authenticated revocation. [S14]

DNS16 — Maintain parent DS with CDS/CDNSKEY

Cases: consistent-update, consistent-ds-removal, one-authority-stale, cds-cdnskey-keyset-disagreement, nodata-versus-removal, unreachable-authority-retry, digest-policy-comparison, dsync-notify-trigger, invalid-dsync-target, malformed-delete-signal.

Acceptance: child intent is observed, authenticated and checked before the parent’s DS changes. Apply RFC 9975’s all-addresses/received-response consistency rules; NODATA counts as a response, while unreachability has retry handling. Compare eligible referenced keys rather than requiring byte-identical RRsets of every digest type. Inconsistency leaves the existing delegation unchanged. A signed, agreed removal request is different from no publication. Explain CSYNC separately: it requests NS/glue synchronization and does not itself request a DS update. [S19, S21]

For deletion, check the authenticated singleton signal (CDS 0 0 0 0 or CDNSKEY 0 3 0 0) and retain child signing until the applicable old-DS cache dependencies have cleared. With RFC 9859, discover the DSYNC target, send the appropriate NOTIFY and then run normal retrieval/validation. A notification acknowledgment is not DS publication. Cover CDS notification semantics for both CDS/CDNSKEY changes and ignored unusable scheme/port entries. [S19, S29]

DNS17 — Bootstrap DS and operate automation safely

Cases: authenticated-rfc9615-bootstrap, unauthenticated-child-only-claim, signaling-zone-not-secure, only-in-domain-nameservers, parent-policy-declines, update-would-break-validation, concurrent-manual-update, report-and-retry.

Acceptance: show RFC 9615 signaling through an already authenticated out-of-domain DNS operator namespace and the consistency/acceptance checks for the claimed child. Make absent parent DS and an eligible out-of-domain NS explicit prerequisites; an all-in-domain set cannot supply the missing independent trust. Do not bootstrap trust circularly from the child’s own untrusted signature. Distinguish manual/out-of-band enrollment and older RFC 8078 policy profiles from the selected authenticated bootstrap. Apply RFC 10026 continuity checks and reporting; chosen temporary DS TTLs must not be presented as instant remote cache invalidation. Show locks and concurrent manual changes as explicit policy inputs. [S19, S20, S21]

Within the existing concurrency/retry cases, preserve a manual recovery channel. In-band DELETE must not suspend automation; out-of-band full DS removal should suspend it until a nonempty DS set is provisioned. Apply the different registrar/registry lock semantics from RFC 10026 §6 rather than equating every update lock with suspended automation. [S20]

DNS18 — Operate multiple signers/providers

Cases: shared-ksk-model, separate-ksk-model, cached-keys-provider-switch, missing-cross-provider-key, coordinated-rollover, provider-migration, conflicting-cds-intent.

Acceptance: demonstrate RFC 8901’s two models with declared private-key custody, DNSKEY sets, DS state and per-provider signatures. A resolver using cached keys from one provider must still have a valid path when it gets an answer from the other. Public-key coordination is not implicit private-key copying. Use RFC 9975 checks to prevent one provider’s automation signal from silently removing another’s delegation support. [S15, S21]

DNS19 — Publish and replicate a signed zone

Cases: offline-signer-secondary, notify-ixfr, axfr-fallback, tsig-authenticated-update, tsig-valid-policy-denied, tsig-failure, zonemd-mismatch.

Acceptance: distinguish management update authentication/authorization, zone signing, transfer and query serving. NOTIFY triggers appropriate checking; it is not the zone transfer itself. Use current TSIG (RFC 8945) for the chosen transaction profile, with explicit shared-key holders and integrity checks; it provides no general confidentiality. A secondary can serve signed public records without a signing private key. For the ZONEMD case, authenticate the expected digest appropriately and demonstrate whole-zone integrity failure separately from individual RRset validation. Do not claim DNSSEC alone authorizes UPDATE or AXFR. [S22, S25]

DNS20 — Diagnose failure and recovery

Cases: bogus-servfail-with-ede, same-failure-without-ede, cd-one-diagnostic-data, transport-timeout, failure-cache-suppresses-retry, retry-after-expiry, temporary-negative-trust-anchor.

Acceptance: log the first detector, internal reason, external RCODE/flags, optional EDE and application outcome. EDE is diagnostic metadata, not signed proof and not an RCODE override. Implement RFC 9520 failure caching as distinct from authenticated negative caching; the chosen bounded duration and retries must meet that standard. A negative trust anchor is an explicit temporary operator bypass with scope/expiry, not a repair that makes data secure. Rechecking after expiry must perform the relevant work again. [S12]

DNS21 — Compact denial of existence

Cases: compact-nonexistent-name, genuine-nodata, empty-nonterminal, co-enabled, co-disabled-downstream, explicit-nxname-query, no-wide-aggressive-synthesis.

Acceptance: implement the selected RFC 9824 NSEC profile: signed NXNAME bitmap evidence, NODATA-shaped answers and optional CO-signaled response-code restoration. NXNAME is not a stored ordinary RR or an RCODE. Track CO per hop and cached response context. Reject explicit NXNAME queries appropriately without forwarding them. The minimally covering proof cannot be used as if it were a broad conventional denial range. Include an explanation of the specified NSEC3 alternative without claiming it is the preferred profile. [S11]

DNS22 — Private DNS, local anchors and conditional forwarding

Cases: private-signed-zone-local-anchor, private-signed-zone-no-covering-anchor, conditional-forward-with-local-validation, different-client-trust-stores, stale-private-anchor, private-view-versus-public-chain.

Acceptance: use two explicit DNS views with named trust stores, routes and fixture identities. Conditional forwarding changes destination selection; it is not an authenticated delegation or anchor bootstrap. A public root anchor does not automatically establish trust in an unrelated private hierarchy. Identical owner names may resolve differently under declared views; do not merge their caches or keys. These are deployment profiles composed from DNSSEC mechanisms, not an assertion that RFCs mandate one split-DNS product design. [S01, S04, S14, S23]

The no-covering-anchor case has no applicable anchor anywhere. The public-chain case instead has a configured public anchor and public-tree evidence conflicting with the private view. Give each its own evidence/reason and expected verdict; do not apply one generic “private zone is insecure” rule.

6. UI and learning ergonomics

Default journey: DNS01 should start with a short question, show the application and resolver immediately, then introduce authority actors as the lookup reaches them. Keep the signer out of the default wire path; offer “How were these records signed?” as a related lesson. Keep full journey, backward navigation, chapter navigation and field following available.

Three existing views: Journey explains decisions; Fields shows actual message/RR structure; Crypto explains covered bytes, keys, digests and numerical evidence. Use progressive disclosure for NSEC3 calculations, canonicalization and rollover timing. Long signatures must not push the inspector heading offscreen.

Trust panel: at the selected event show “Data received,” “Checked by,” “Trust starts at,” “Current status,” “Reason,” and “What the application received.” Label remote assertions separately from local verification. Use text and icons as well as color. “Insecure” needs a short explanation such as “No authenticated chain for this data”; it must not imply proven forgery.

Time: lifecycle lessons need an explicit protocol clock plus cache/signature/hold-down markers. Play/pause animation time is not protocol time. A “jump ahead” event must explain the elapsed interval and resulting state changes. Never show a future cache entry as currently held when seeking backward.

Controls: use authored variants with valid combinations, clear defaults and short scenario labels. Avoid a giant unconstrained matrix of DO/CD/AD/anchor/transport toggles. Provide a focused flag comparison in DNS05/06 with query and response columns. Searches for DNS, DNSSEC, signing, forwarder, resolver, DS, NSEC, trust anchor and rollover should find the relevant lessons.

Accessibility: keyboard operation, focus restoration after changing variants, reduced motion, mobile touch, browser zoom and both themes need real UI checks. Human comprehension prompts should ask who validated, whether an insecure result is the same as bogus, and why a rollover broke one cache but not another. Carry G01 forward honestly; automated accessibility data cannot substitute for speech/comprehension acceptance.
