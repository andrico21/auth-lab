DNS-R10 — P2: secure alias cache inherits target-failure metadata

Required correction. Select DNS09 / cname-bogus-target and reach accepted-use-and-cache-boundary (source index 29 in this candidate). The CNAME RRset has been authenticated, while the target fails validation. Overall resolution correctly returns SERVFAIL/refuses the target address. The model deliberately retains the secure CNAME cache independently.

At protocol time T = 1792713600, the separate alias cache contains contradictory data:

Field Secure alias cache, actual Correct meaning at this boundary

The alias’s authenticatedProofDeadline also inherits null from the failed aggregate entry. Audit that related field against its documented per-entry meaning when constructing the alias cache; do not carry target-failure metadata into an independently authenticated alias record by accident.

Cause and bounded fix

In src/dnssec-denial-cases.js, around lines 310–321, the aggregate result entry is built from the failed end-to-end lookup. aliasEntry then spreads that entry and replaces the alias’s kind, security status, expiry, signature bound and evidence references, but retains the aggregate failure’s remainingTtl and validatedAt.

Construct the alias cache from its own authenticated alias tuple and validation event. At creation, derive its remaining TTL from its own effective expiry and the represented clock, and give it the actual alias validation timestamp. Keep its received tuple, signer/zone, evidence references, cache key, owner, original receipt and signed Original TTL intact. Review other fields inherited by the same spread for the same ownership/lifetime error, particularly authenticatedProofDeadline.

Preserve the failed target’s five-second failure cache and the overall SERVFAIL/application refusal. The independently retained secure CNAME continues to have its original 300-second lifetime. Do not make the alias share the target failure deadline to conceal the inconsistency, invent another network exchange or signature check, or change signed bytes.

This finding concerns internal protocol-state and teaching consistency. RFC 4035 §5.3.3 supplies the authenticated RRset lifetime context; it does not prescribe JavaScript property names. The current worksheet already says the authenticated CNAME can remain separately cached with its original expiry, and that target failure must not rewrite alias origin or confer target trust.
