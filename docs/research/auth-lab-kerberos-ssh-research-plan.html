1. Recommended product shape

Keep one distributable HTML. Web sign-in, SSH access and Kerberos are entry points into one scenario registry/player. SSH opens a filtered catalog. Kerberos opens sibling family cards AD DS Kerberos and Kerberos → Keycloak. Global search opens the scenario’s owning workspace; a bridge has one scenario ID and one continuous OIDC transaction.

Scope correction from review C00/C19: standalone AD DS, PKINIT, FAST and multi-forest trust/referral demonstrations are required deliverables. They may arrive in separate milestones, but Kerberos is not complete until they are delivered and verified. A cached-TGT introduction or Keycloak integration alone does not satisfy that scope.

OAuth/OIDC establishes identity or authorizes credential enrollment; SSH then uses its own authentication mechanism. The IANA SSH registry has no native OAuth/OIDC method. This describes registered methods, and does not exclude vendor extensions. [1]

The taxonomy is a proposed teaching design. Availability and exact packets depend on the selected implementation; every vendor profile must carry a version/support badge. Start with successful paths, then expose named failure demonstrations in an optional panel.

Three distinctions must be visible from the first screen. A Kerberos realm is different from a Keycloak realm. A successful IdP login is different from permission to enter a Linux account. Enrollment MFA, SSH key possession and per-session MFA are separate checks.

2. Kerberos workspace

Participants and boundaries

Standalone AD DS uses Person, Workstation/Windows credential context, DC/KDC (expandable AS/TGS), Domain service and AD identity/policy data. User and computer accounts are separate logical owners. The bridge additionally uses Browser, Keycloak and Application. Forest boundaries contain their own domain/KDC components; a configuration trust edge is different from an active exchange. Microsoft places Kerberos operations in the OS security stack. [2]

WorkstationSeparate user/computer credentials, local keys, Windows context and cache state
AD DS infrastructureDomain/KDC identities, krbtgt/trust keys, service-account SPNs and policy
Domain serviceService-account key context, proof/replay processing and final resource authorization

MIT ccache/keytab terminology remains available in generic/Keycloak profiles, but is not a specification of Windows credential storage. Do not require a Unix-style keytab on every Windows service. Inspect credentials as ticket plus associated session material; retain separate local stores and protection boundaries. [3] [4] [5]

Password and PKINIT are alternative initial-authentication paths. FAST protects applicable KDC exchanges; it is not a later factor or protection for application traffic. Required separate lessons do not imply every PKINIT+FAST or cross-forest combination is supported.

AD-01 - First sign-in is the introductory default

Start with no usable user credential and explicitly stated domain-joined computer prerequisites. Cached SSO is a separate preset. For the ordinary Windows password path, include PA-ENC-TIMESTAMP in the first AS request and the applicable PAC request. An empty request/retry is a separately evidenced variant. [45]

  1. Local password processing and initial AS.Derive/select the client reply key locally, protect preauthentication, validate at KDC and return the TGT plus separately protected client reply.
  2. Store the full credential.Retain ticket and session-key object continuity. The user does not receive krbtgt or service-account long-term keys.
  3. Complete local Windows logon.For a literal interactive Windows profile, include the workstation host/ service credential and PAC consumption required for local sign-in before the subsequent remote-service lesson. A trace omitting this must be titled credential acquisition rather than complete Windows logon. [53]
  4. Resolve the remote SPN and request its credential.Show the SPN’s service-account binding, client TGS request, returned service credential and cache insertion.
  5. Authenticate to the service.Present the credential with fresh proof; process selected mutual authentication. Expose the relevant local inputs/checks without inventing omitted SMB/SSPI packets.
  6. Decide resource access.Show selected PAC SID/group information under ticket authorization-data and a separate service access decision; any online PAC-validation leg requires its own service evidence. [56]

The exchange outline follows Microsoft’s protocol overview. [2] Canonical Kerberos containers remain separate from bearer tokens. Modern TGT PAC requirements must not be replaced with a universal “include-pac=false removes the PAC” switch. [56]

KC-01 - Corporate desktop SSO → Keycloak → OIDC application

Reuse the app’s ordinary authorization transaction. When Keycloak authenticates the user, the browser/OS reuses a valid cached service credential or obtains a ticket for Keycloak’s HTTP service and performs HTTP Negotiate. Keycloak maps the accepted principal into a user and resumes its OIDC response. The app receives its existing code/token result, with no raw desktop credentials traveling to it.

HTTP Negotiate can require several exchanges and a final server token; the example HTTP service principal is HTTP/hostname. RFC 4559 is Informational, not an OAuth grant. [7] SPNEGO envelope fields include mechTypes, mechToken, supportedMech and responseToken; the initiator should omit reqFlags, and the acceptor must ignore it. [8] GSS context setup is a local API operation; channel binding and delegation depend on mechanisms and deployment policy. [9] [10]

Keycloak documents SPNEGO with HTTP keytab setup, LDAP federation or a Kerberos-only user provider; the latter lacks complete profile data. NTLM is not supported. Its current guide marks Kerberos credential delegation deprecated, so delegated credentials in application-token claims are excluded from the ordinary preset. [11]

KC-02 - Kerberos + explicitly enforced assurance

Stock Keycloak Kerberos execution is disabled. [11] Name the comparison Why OTP can be skipped after enabling Kerberos as Alternative in a default-derived flow. The documented alternative-execution example explains that bypass; it is not an untouched-default configuration. [12]

The introductory assurance contract requires a fresh second-factor ceremony per new application authentication transaction; a separately named comparison may permit sufficient assurance within a stated age. Both need an exact tested realm/flow export, browser binding, client override and claim mapping. Reuse existing TOTP/WebAuthn ceremonies. Do not assume “put OTP next” guarantees enforcement, or fabricate automatic acr="mfa"/amr=["kerberos"]. RFC 8176 registers wia for Windows integrated authentication. [13]

Failure placement and browser eligibility

AD-05, AD-06 and KC failures belong to their owning family. Fresh proof, cached state, trust, identity mapping and assurance have distinct stopping points. The same error label must not conceal them.

Browser integrated-auth eligibility is a policy prerequisite; an explicit allowlist or browser intranet rules may provide it. Being domain joined alone does not permit every origin. Delegation allowlisting is a separate control. [14] [15] Show fallback only when the selected Keycloak flow actually permits it.

AD DS trust/referral presets are required scope. KILE does not check transited domains at its KDC/application server and servers ignore TRANSITED-POLICY-CHECKED; do not import a generic RFC transited-policy check into the Windows lesson. [51]

3. Main SSH journey - OIDC enrollment → OpenSSH certificate

Use a named Smallstep / step-ca profile first. Its CLI login and OIDC enrollment are documented, while the target can remain ordinary OpenSSH. The current provisioner documentation states browser Authorization Code + PKCE and Device Grant support. A distributed native-client secret, when present, does not confer confidential-client security properties. [16] The CLI can create a keypair and load the resulting credentials into ssh-agent. [17]

Actors: Person; Enrollment CLI; Browser; Keycloak/IdP; SSH CA; SSH client; Local agent/key store; Target host (sshd). Fold the agent into the workstation by default; expand it when a key-possession attribute is selected. Optional Entra/Okta brokering happens within the existing IdP-authentication portion. A named external-provider profile must validate its own client and claim support.

  1. Show configured trust.CA → accepted OIDC issuer and enrollment client. Target → trusted SSH user CA. Workstation → trusted target host key or host CA. Use three distinct trust edges.
  2. Create/select an SSH key locally.Show public key generation or selection; keep the private key in local software or hardware. Later signing acts on the key without sending it away.
  3. Create the OAuth transaction locally.CLI prepares state, nonce, code_verifier and S256 code_challenge, then opens the external browser with its authorization request.
  4. Authenticate at the IdP.Default corporate preset: password + TOTP. Allow dedicated passkey and external-IdP presets. Existing SSO is a policy-dependent branch, not proof of freshly performed MFA.
  5. Return to the CLI loopback receiver.Browser delivers code and state; CLI checks callback state, exchanges the code with the verifier at the token endpoint and receives the ID token. The CA independently validates that token before issuance. Do not put tokens on the Authorization Code callback arrow.
  6. Request SSH enrollment.In this vendor profile send publicKey and ott to step-ca; the OIDC enrollment credential is the ID token. Optional requested principal/time settings remain proposals subject to CA policy.
  7. Validate and authorize issuance.Show issuer, signature, audience and token-time checks; then map identity to allowed SSH principals and limits. Separate identity acceptance from privilege authorization.
  8. Issue and install the certificate.The CA signs the public key and policy/time metadata; the CLI receives the certificate and installs/selects the local key-and-certificate pair.
  9. Establish SSH transport and verify the host.Show key exchange, host proof and trusted-host decision before user authentication. Stop here on a host-identity failure.
  10. Prove possession to sshd.Client sends certificate using SSH publickey and signs authentication data with the matching private key. The signature is tied to this SSH connection.
  11. Check host authorization and open the session.Host checks its certificate trust/policy and local account, verifies user proof, then opens the requested channel only after authentication succeeds.
  12. Compare later states.Advance simulated time: expired credential blocks a new authentication. An already established session has its own lifecycle and enforcement policy.

Native external-browser/loopback behavior follows RFC 8252, and verifier/challenge checks follow RFC 7636. PKCE protects code redemption; it does not prove SSH private-key ownership or supply MFA. [18] [19]

Smallstep’s OIDC implementation accepts the provisioner client’s identity token: expected aud is its configured client ID, with issuer/signature/time and applicable azp checks. This is an explicit vendor enrollment contract, not generic ID-token API authorization. [20]

The inspected step-ca API has mandatory publicKey/ott, optional certType, keyID, principals, validAfter/validBefore, and response crt. It does not mandate a signed SSH CSR. Optional identityCSR concerns a separate X.509 request. [21]

Freeze sanitized request/response fixtures: publicKey and crt encode base64 SSH wire bytes, not PEM CSRs or authorized_keys text. Keep decoded local inspectors separate. CA HTTPS server trust is independent of its SSH signing key. Token-use bookkeeping needs same-release inspection: CLI transaction nonce, CA validation and replay/consumption are separate owners; a CA replay identifier does not prove comparison with a CLI transaction nonce. [21] [61]

Actual SSH proof uses SSH_MSG_USERAUTH_REQUEST, username, ssh-connection, publickey, boolean TRUE, algorithm, key/certificate blob and signature. Signing covers the session identifier and request; an unsigned query uses FALSE and is optional, not completed authentication. [22] The first exchange hash supplies the session identifier, which persists across rekeying. Transport and host authentication remain a separate layer. [23]

Certificate and host policy

Badge deployed *-cert-v01@openssh.com credentials as OpenSSH extension, not an RFC 4252 certificate schema or an X.509 certificate. Inspect public-key material, certificate nonce, serial, type, key id, valid principals, valid after/valid before, critical options, extensions, signature key and CA signature. Unknown critical options reject; unknown extensions can be ignored. [24]

Host static policy includes TrustedUserCAKeys, configured principal mapping, RevokedKeys/KRL and a valid local account. CA signature validity alone is insufficient. User-CA trust and host-CA trust are independent; do not teach a user certificate as establishing server trust. [25]

Use fresh user-certificate enrollment/reissuance for the Smallstep lifecycle. The SSH renewal command is for host certificates, not user certificates. [39] Reissuance creates a new certificate instance/serial/validity; a reused public key retains its own identity. Whether a new ceremony is needed is an explicit assurance policy.

Headless CLI variant

Reuse the Device Flow model when the enrollment CLI lacks a local browser: CLI owns the transaction, separate browser authenticates, then CLI requests the SSH credential. Provider/client/provisioner compatibility remains explicit. RFC reference cases must be separate from literal product behavior. The retrieved live Smallstep CLI maps 4xx token responses to one retry sentinel and repeats at the same interval; it does not establish release-conformant pending/slow-down/terminal-error handling. [40] Freeze and exercise the chosen CLI before claiming exact fidelity.

The reference Device lesson has pending cadence, repeated slow-down, timeout backoff, terminal errors and cancelled/restarted transactions. Keep a visible user code and textual URI even with a shortcut/QR-style complete URI; compare the product presentation separately. Reference polling follows RFC 8628, with no loopback receiver or PKCE. [26]

Four lifetimes and three factor locations

Add a synchronized mini-timeline for IdP SSO session, OAuth token, SSH certificate and established SSH session. Expose Advance time, IdP logout, Disable user and Revoke certificate at host as fixed demonstrations. Simulated clock changes must be independent of playback speed.

Inference from the separate verification layers: ordinary offline certificate verification does not acquire immediate knowledge of IdP logout or group removal. An issued credential, future enrollment and an existing connection therefore need separate outcomes. Host revocation distribution or an online access service can change enforcement.

OIDC auth_time describes end-user authentication; iat describes issuance. Reusing SSO is not necessarily fresh MFA. Use max_age, supported acr_values and validated claim/policy mappings, rather than displaying an automatic MFA badge. [32]

Separate browser MFA at enrollment, hardware-backed SSH signing, and access-service per-session MFA. OpenSSH security-key credentials generally use an SSH application context such as ssh:; an IdP passkey has a different RP/origin context. The same YubiKey can hold distinct credentials. OpenSSH also supports a special WebAuthn signature format, so avoid saying WebAuthn can never participate in SSH. Touch alone does not establish an arbitrary MFA policy. [33]

Protocol assertions

  • Private SSH keys, CA signing keys and keytab material never appear as ordinary transmitted secrets. A certificate copied without its matching private key cannot complete user proof.
  • No OAuth token reaches ordinary certificate-authenticating sshd. The CA signature and client authentication signature are distinct objects and checks.
  • SSH host verification precedes SSH user authentication. In the server-side Device preset it also precedes browser approval. Certificate enrollment can occur before any target connection.
  • Wrong ID-token audience blocks Smallstep enrollment; wrong SSH principal blocks host authorization. Token aud, Kerberos service principal and certificate principals are never interchangeable.
  • Kerberos ticket issuance, cache storage and later presentation retain object identity; fresh authenticators and replayed authenticators have intentionally different outcomes.
  • SSSD prompt transmission excludes its private OAuth transaction fields. An approved browser account different from the requested SSH identity can fail; IdP success alone does not bypass local account policy.
  • Normative Device reference handles pending, slow-down, timeout and terminal errors. Literal product traces retain observed behavior and are labeled separately. Loopback/PKCE occur only in the applicable code branch.
  • MFA policy is enforced on every success path, including cookie reuse, fresh user-certificate reissuance and failed factors. The bypass comparison explicitly enables Kerberos Alternative in a default-derived flow.
  • Seek backward/forward reproduces the same caches, revocation knowledge, simulated clock and session outcome as straight playback to that point.

AD-04 - FAST AS and TGS protection

Question: which KDC data is protected by armor, and whose credentials provide it? Use separate computer/user credential instances. Microsoft documents computer TGT armor for user AS and user TGT armor for ordinary TGS. [44] Required armor policy still permits the computer bootstrap AS exception; do not reject every unarmored request. [46] Domain/client configuration, realm capability and suitable DC discovery are explicit gates; required policy cannot silently fall back. [47]

The nested reference exposes PA-FX-FAST, armor, req-checksum, enc-fast-req, protected inner padata/body and enc-fast-rep. Derive armor locally; never transmit its key. Password FAST uses PA-ENCRYPTED-CHALLENGE (138), with distinct client/KDC challenge keys. Protected response checks nonce/finished and strengthens the reply key; ticket-session keys remain separate. Ordinary TGS keeps outer PA-TGS-REQ, implicit armor, required authenticator subkey and its own checksum input; preserve that subkey’s original reply-key role during mandatory TGS strengthening. Error replies omit strengthening. FAST does not protect subsequent application traffic or universally hide every outer name. [43]

Authoring outputs: a request/response nesting fixture with exact byte-representation references, key derivation inputs and key-usage checks; separate AS and TGS layer views; capability/policy branch. Focus reveals the correct encrypted/decoded layer and owner. Useful rejections: missing required armor, unsupported realm/DC, broken checksum/ciphertext, wrong challenge, missing protected response and mismatched nonce/ticket. Seek restores credentials, derived-key identities, capability knowledge and completed checks. PKINIT+FAST and compound-identity TGS require their own evidenced combination and are not inferred from standalone successes.
