## Navigation and teaching surface

- **Workspace or family** is a grouped searchable combobox. A separate **Universal lab scenario** search retains global ID, workspace, family, title, case, profile and canonical-field discovery. Deliberate activation opens the destination; filtering or moving its highlighted option must not change the active lesson or playback. Existing native text editing, composition, menu dismissal and logical focus recovery remain required.
- The beginner surface puts the **learning question, starting identities/credentials/trust, finish boundary, Play and a useful first flow** together rather than behind several screens of menus. This is the interface contract, not a claim that all viewport/zoom gates have passed.
- **Ready-made journeys**, the scenario library and advanced settings remain expandable below the flow. **Cases, profile, primary sources and related journeys** contains the active lesson's case controls, detailed profile/support caveats, references and related journeys. Question/start/finish context remains near Play.
- Play, Reset and speed remain above the graph. **Map display options** follows the graph, keeping the step-name, internals and held-object toggles visible and reachable without crowding the mobile first flow. Their labels retain 44-pixel targets; no introductory text is hidden or reduced to make the layout fit.
- Journey, Fields and Crypto are detail views of the same protocol state. The field pane stays open by default. Profiled lab lessons initially show their journey's fields; Core and Web presets retain the full catalog. Typed field search is global, and clearing restores that lesson's normal scope. No performance claim may be based on closing the pane or removing field controls.
- Related navigation starts a fresh authored destination context. It does not transfer a TGT, token, local session or privilege. Folding components changes presentation, not logical ownership. Exact held-object inspection/replay must distinguish local creation, Local IPC, network transfer, receipt, verification and acceptance, including rejected results and preserved local sessions.

The [navigation contract](navigation.md) supplies the implemented route, keyboard, focus and native-collection requirements; the implementation ledger traces authored scope separately from runtime evidence.

## Source applicability and model boundaries

Use the [primary source ledger](source-ledger.json) with [source-disposition.json](source-disposition.json), not a source URL or HTTP 200 alone, to establish retained bytes, exact source-row identity, selected revision/section, supplemental or replacement applicability and unresolved limitations. The disposition distinguishes core-required, optional-only and catalog/profile-only sources. Frozen references and later supplements retain their identities; retained documentation is not proof that a native platform supports a feature.

Profiles are explicit inputs to a lesson, not universal defaults. Per-case overrides and inherited row profiles are traced in the implementation ledger and worksheets. In particular:

- **NFS** fixes version, security flavor, transport and supported optional features. Its Linux-oriented standards profile makes no tested-kernel claim. RPCSEC_GSS protection, TLS transport, identity mapping and export/file authorization are distinct boundaries; neither successful authentication nor encrypted transport implies permission.
- **Windows** models declared authentication packages, credential custody, access tokens, admission and elevation. The pinned Windows build is reference-only, with no installed-build/token/log evidence. Administrator Protection policy applicability retains the documented source discrepancy; it is not a native support/default claim or generic UAC substitute.
- **Unix** composes declared NSS/PAM/SSSD/systemd, sudo/polkit/kernel-policy and Apple profiles; it is not an installed distribution or macOS deployment. Local sign-in, directory identity, offline cache, network credentials and resource authorization stay separate. The Unix resource fixture is an explicitly **lab-owned RFC 4120 TGS/AP exchange plus KRB_PRIV-protected READ request/result**. It is not an installed SMB, NFS or OS resource-access result. Its supplemental `next-unix-KRBRESOURCE` source applies to LLOG05 and MLOG04; it makes no historical DES, numerical-cryptography or native-service claim.
- **JWT** separates readable untrusted representation, configured algorithms/keys, signature or authenticated decryption, claims, purpose and application authorization. Demo cache lifetimes, skew and required claims are selected policy, not universal RFC or Kubernetes defaults. See the [JWT policy contract](jwt-policy-contract.md).
- **Kubernetes** separates external credential acquisition, API authentication/claim mapping, request authorization, admission and workload or extension trust. Pinned manifests and source predicates are fixtures, not evidence of a running cluster.
- **MCP** uses its dated authorization/draft profiles and distinguishes HTTP authorization, independent upstream grants, stdio and host/tool policy. A valid access token is not permission to execute every tool, and a lesson does not certify a deployed client/server.

The standalone player uses symbolic teaching values and simulated cryptographic decisions, not production credentials or live authentication. Separate numeric QA can establish only the vectors/constructions it actually executes; it does not turn every symbolic field into a cryptographic test or establish native interoperability. Browser-native execution means the app ran in a browser, not that Windows, Linux, macOS, NFS, an issuer, a Kubernetes cluster or an MCP service was exercised.
