# JWT fixture-policy contract - revision 1

Pure offline teaching policy; no network, clock reads, production signature verification or runtime cryptographic dependency. Imports from `src/jwt-policy.js` are family-prefixed and stable.

## Public API

- `jwtParseCompact(compact, {representation = 'jws'} = {})`: returns `{ok,stage,code,header,claims,signingInput,segments}` for JWS, header/envelope only for JWE, or opaque bytes. No trust. Strict compact segment/base64url/UTF-8/object JSON and duplicate-key rejection. Segment counts refer only to compact serialization. Opaque selection is explicit, never inferred from OAuth field names.
- `jwtValidateFixture({token,profile,keys,signatureEvidence,now,discovery})`: token is `{compact,instanceId}`. Profile is `{id,issuer,audience,algorithms:['RS256'],requiredClaims:['iss','sub','aud','exp'],skewSeconds:0,maxAgeSeconds?,maxLifetimeSeconds?,numericDateMax?:100000000000,audienceArray:true,purpose:'generic'|'oidc-id'|'kubernetes-id'|'service-account'|'rfc9068-access',nonce?,requiredClaimValues?,claimTypes?,processedCriticalHeaders:[]}`. Keys are issuer-local public metadata `{id,kid,issuer,kty:'RSA',alg:'RS256',use:'sig',key_ops:['verify']}`. No private material. Signature evidence is explicitly authored `{kind:'SYM',valid:true|false,tokenInstanceId,keyId,signingInput,signatureSegment}`; it must bind exact token generation, encoded signing input, signature segment and selected key. It does not establish mathematical validity. `discovery`, when provided, is `{issuer,jwks_uri,expectedJwksUri,httpsTrusted:true}` and must match configured issuer/trusted URI. Token `jku`/`x5u` are rejected, not fetched.
- Validation returns `{ok,stage,code,observations,untrustedClaims,validatedClaims:null|object,keyId,signatureValid}`. Stages: `parse`, `trust`, `header`, `key`, `signature`, `claims`, `accepted`. Only accepted exposes validatedClaims; no principal, login session, authorization or RBAC grant is created. Consumers own mapping/authorization independently. `observations` retain actual check results. All registered claims are not universally required; profile requirements are explicit. RFC9068 requires at+jwt/application/at+jwt and its required claims. OIDC/Kubernetes do not require invented typ=id_token. No purpose inference from token origin.
- `jwtDecryptFixture({token,recipientKeyId,evidence})`: outer JWE parameters must be RSA-OAEP-256/A128GCM/cty JWT; explicit `{kind:'SYM',valid,tokenInstanceId,recipientKeyId,compact,innerCompact}` evidence binds envelope/key. Returns `{ok,stage,code,innerCompact?}`. Failed AEAD/key check returns no plaintext. Success alone does not validate the inner signature/claims.
- `jwtRefreshDecision({cache,kid,now,policy})`: pure issuer-scoped bounded refresh transition, returns `{action,code,cache}`. Cache `{issuer,keys,fetchedAt,lastRefreshAt,inFlight,startedAt,negativeKids:[{kid,until}]}`. Policy defaults TTL300s, minimum interval30s, timeout2s, negative TTL30s/capacity16. `jwtCompleteRefresh({cache,keys,now,ok,policy})` completes explicit fetch evidence; no fetch occurs. Actions `cached`, `refresh`, `coalesced`, `deny`. Stale keys never accepted. Demo timings are not Kubernetes implementation defaults.
- `jwtIntrospectionDecision({response,authenticated,expectedAudience,now,cachedAt,ttlSeconds:15,timeout:false})`: checks protected response, cache age, active, audience and exp. No JWT signature or sender binding claim.

## Boundaries and evidence

Readable JWS payload is untrusted until acceptance. JWE receipt yields ciphertext only; recipient-local unwrap creates inner JWS readable-untrusted, then signature and claim checks are separate. Bearer reuse within lifetime is allowed without explicit sender constraints/replay state; jti alone provides neither. Local JWT checks do not introspect or revoke tokens on logout. Refresh tokens remain client/plugin-local and issuer signing keys issuer-local. Inputs are synthetic; decoded encoded bytes are not numerical proof. Numeric QA uses isolated retained RFC vectors and independent crypto implementations; neither numeric QA nor fixtures prove live-platform conformance.

## Integrated authoring surface

`src/jwt-validation-lab.js` exports `JWTLAB_ATTRIBUTES`, `JWTLAB_SOURCES`, `JWTLAB_SCENARIOS`, `createJWTScenario(numberOrPlanId, variantId = 'default')` and `createJWTNegativeFixture(numberOrPlanId, namedVariant)`. All nine frozen IDs are `lab-jwt01` through `lab-jwt09`; named cases preserve their parent picker ID. Each model exposes immutable fixture inputs, source-owned `jwtInventory`, `catalogAttributeIds` (including explicitly declared branch-only fields), `decisionBindings`, `variantChoices` and `withVariant`. Default construction does not eagerly build negative models.

`src/held-object-jwt.js` exports `buildJWTHeldObjects(args)`. Register the JWT source-array owner and this builder in both parent dispatch maps. Each repeated receipt has a distinct request-scoped holding identity while retaining the exact same bearer artifact and wire bytes. Decrypt and claim acceptance preserve distinct representations and source prefixes.

The public canonical namespace is `jwt`. The compact strip reads only `untrustedStatus`, `signatureValid`, `claimsAccepted` and `purposeStatus`. Other explicit leaves include `validatedClaims`, `principal`, `authorized`, `decrypted`, `failure`, `failureDetector`, `clientKnowsFailure`, `serverKnowsFailure`, `completedActions`, `clientLogin`, `resourceClaimsAccepted`, `cachedOldAccepted`, `oldKeyRetired` and the fixed fixture clock. Client-login acceptance does not imply API acceptance. A later bearer denial preserves the earlier completed actions and already-received results.

Refresh pending tracking has the same 16-entry bound as the negative-cache teaching policy. New distinct requests beyond pending capacity receive `deny / refresh-bounded`; tracked concurrent requests coalesce without a new fetch. JWT06 reserves the original generation2 pending slot before all 32 unknown-kid arrivals. Each arrival retains its exact request instance/kid and decision; the first excess is `flood-token15 / unknown15`. Capacity errors deny those requests, not the admitted original. All 32 arrivals are evaluated. A timely successful JWKS response at now+1 permits original generation2 signature and claims validation only after receipt and cache installation, including when the initial cache is stale. Fresh unrelated issuer-bound cached keys remain independently usable; stale old-token material does not. The negative-cache completion helper retains a bounded set of missing kids. The retired/stale key material may remain in historical custody, never newly accepted merely because it is still inspectable.

JWT03 selects a held private-key representation with stable `{id,handle,alg,use}` metadata. Default selection is `recipient-generation1`; wrong-recipient actually holds `recipient-other` with a distinct private-key handle. The unwrap operation consumes that exact artifact, passes its `id` to the policy, and records the selected artifact ID/key ID separately from the generation1 encryption public key and original envelope evidence. Wrong-recipient and changed-tag acquire neither CEK nor inner plaintext. Authenticated unwrap still precedes the independent inner signature check.

It verifies only those declared mathematical claims. It does not verify the runtime SYM fixtures, RSA-OAEP-256 key transport, a full nested JWE profile, native-browser behavior or live platform interoperability. Parent owns script/CI registration, emitted bundle freshness and all mounted/native gates.
